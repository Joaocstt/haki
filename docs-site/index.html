Introdução

Conheça o Haki

O Haki é um miniframework PHP para criar APIs REST. Ele cuida de tudo o que se repete em toda API (rotas, leitura da requisição, respostas JSON, validação, login com token e tratamento de erros) para que você escreva só as regras da sua aplicação.

A ideia é ser simples o bastante para quem está começando e organizado o bastante para crescer. Uma API funcional cabe em poucas linhas:

routes/api.php
/** @var Haki\Haki $app */

$app->get('/ola/{nome}', function (string $nome) {
    return ['mensagem' => "Olá, $nome"];
});

Acessando /ola/Shanks no navegador, a resposta é:

{ "mensagem": "Olá, Shanks" }

O que é uma API REST, em poucas palavras

Uma API é um programa que não mostra telas: ele recebe pedidos e responde com dados. Quem faz os pedidos é outro programa, como um site em React, um app de celular ou outro servidor.

Cada pedido (uma requisição) tem duas partes principais:

  • O método, que diz o que se quer fazer: GET (buscar), POST (criar), PUT/PATCH (alterar), DELETE (apagar).
  • O caminho, que diz sobre o que: /produtos, /produtos/10.

A API devolve uma resposta com um código de status (200 deu certo, 404 não encontrado, 401 não autenticado...) e, normalmente, dados em JSON, um formato de texto que qualquer linguagem entende.

exemplo de conversa com uma API
GET /produtos/10                  ← o cliente pede o produto 10

HTTP/1.1 200 OK                   ← a API responde: deu certo
{"id": 10, "nome": "Chapéu de palha", "preco": 49.9}

O que o Haki faz por você

Quando uma requisição chega, o Haki segue sempre o mesmo caminho:

  1. Encontra a rota certa para o método e o caminho (ou responde 404/405).
  2. Roda os middlewares: código que se repete em várias rotas, como CORS e logs.
  3. Confere o login, se a rota exigir, validando o token JWT.
  4. Valida os dados enviados, se você pedir, respondendo 422 com mensagens claras.
  5. Chama o seu código (o controller), entregando tudo o que ele pediu.
  6. Transforma o retorno em JSON e envia a resposta.
  7. Se algo der errado em qualquer etapa, responde com um erro padronizado, sem expor detalhes internos em produção.

Tipado de ponta a ponta

O PHP permite escrever código sem tipos, e muitos frameworks deixam assim. O Haki faz o contrário: ele usa os tipos que você escreve para fazer trabalho por você, e pode exigir que todo o projeto seja tipado.

OndeComo o Haki usa os tipos
Parâmetros da rotafunction show(int $id): "10" vira o número 10, e /produtos/abc responde 404 antes do seu código rodar.
Injeção de dependênciasO tipo do parâmetro diz o que entregar: Request $request, Auth $auth, ProdutoRepositoryInterface $produtos.
Validação$rule->integer() entrega int, $rule->date() entrega DateTimeImmutable, $rule->enum(Plano::class) entrega o enum. Nada chega como texto solto.
Arquivos geradosTudo o que o init e o make:request criam já vem com declare(strict_types=1) e tudo tipado.
Tipagem obrigatóriaCom $app->requireTypes(), um método sem tipo faz a API responder com erro, dizendo a classe, o método e a linha. O haki check aponta antes de publicar.
 
public function show($id)                 // sem tipo: com requireTypes(), a API recusa e diz a linha
public function show(int $id): array      // tipado: o Haki converte o {id} e confere o retorno

O resultado é menos erro escondido: um valor errado aparece na hora, com uma mensagem clara, em vez de virar um bug difícil de achar depois. Veja tudo em Tipagem.

Por que usar o Haki?

  • Pouca coisa para aprender. São poucas classes, e os nomes dizem o que fazem: Request, Response, Auth.
  • Começa em um comando. php vendor/bin/haki init cria a estrutura do projeto com um exemplo funcionando.
  • Erros que ensinam. Em desenvolvimento, cada erro vem com uma dica em português explicando como resolver.
  • Validação fácil. $rule->cpf(), $rule->email(), $rule->text()->length(3, 100), com mensagens prontas em português.
  • Login pronto. JWT com refresh token, logout e perfis de acesso, sem bibliotecas externas.
  • Tipado de ponta a ponta. Os tipos que você escreve convertem os dados, escolhem o que injetar e podem ser exigidos em todo o projeto.
  • Nenhuma dependência. O pacote usa apenas extensões nativas do PHP.

O que você precisa saber antes

  • PHP básico: variáveis, funções, arrays e classes. Não precisa ser avançado.
  • Usar o terminal para rodar comandos como composer e php.
  • Noção de JSON. Se nunca viu, ele parece um array do PHP: {"nome": "Nami", "idade": 20}.

Para testar a API, você pode usar o navegador (para GET), o comando curl ou programas como Insomnia, Postman ou a extensão Thunder Client do VS Code.

Instalando com o Composer

Crie uma pasta para o seu projeto e, dentro dela, rode:

composer require shankscode/haki

O Composer cria a pasta vendor/ com o framework dentro (vendor/shankscode/haki) e o comando vendor/bin/haki. Para criar as pastas e os arquivos da sua aplicação, rode php vendor/bin/haki init (veja o passo a passo abaixo).

Erro comum

Se aparecer a mensagem abaixo e a pasta vendor/ não for criada, a extensão zip está desativada. Ative-a como mostrado acima e rode o composer require de novo.

Failed to download shankscode/haki from dist: The zip extension and unzip/7z commands are both missing, skipping.

Sua primeira API em 5 minutos

  1. Instale o Haki em uma pasta vazia 
    composer require shankscode/haki
  2. Crie a estrutura padrão do projeto 
    php vendor/bin/haki init

    O comando cria as pastas app/, bootstrap/, routes/, public/ e storage/, os arquivos .env e .gitignore, e já deixa uma rota e um controller de exemplo funcionando. Ele também configura o autoload no seu composer.json.

  3. Suba o servidor embutido do PHP 
    php -S localhost:8000 -t public
  4. Acesse no navegador ou no terminal 
    curl http://localhost:8000/
    { "mensagem": "Bem-vindo ao Haki!", "caminho": "/" }

    Pronto, sua API está no ar. A próxima página explica cada arquivo criado.

Nota

O -t public diz ao PHP que só a pasta public/ fica acessível pela web. Assim, o .env, o código e o banco de tokens nunca podem ser baixados por alguém de fora.

Dica

O init nunca apaga nada: se um arquivo já existir, ele é mantido. Para recriar os arquivos padrão, use php vendor/bin/haki init --force.

Servidores web

Em produção, aponte a raiz do site para a pasta public/ e redirecione todas as requisições para o index.php.

    }

    location ~ \.php$ {

        fastcgi_pass unix:/run/php/php8.3-fpm.sock;
        fastcgi_param SCRIPT_FILENAME $realpath_root$fastcgi_script_name;

Apache

public/.htaccess
RewriteEngine On
RewriteCond %{HTTP:Authorization} .
RewriteRule .* - [E=HTTP_AUTHORIZATION:%{HTTP:Authorization}]

As duas linhas do meio repassam o cabeçalho Authorization, que alguns Apaches descartam e que é necessário para o JWT.

Estrutura de pastas

A estrutura recomendada

O Haki não obriga nenhuma estrutura, mas seguir esta deixa o projeto fácil de entender, de testar e de crescer. Cada pasta tem uma responsabilidade só.

minha-api/ ├── app/ │ ├── Controllers/ recebem a requisição e devolvem a resposta │ ├── Requests/ classes de validação (make:request) │ ├── Services/ regras de negócio (login, cálculo, envio...) │ ├── Repositories/ acesso a dados (banco, API externa, arquivo) │ ├── Contracts/ interfaces que os serviços usam │ ├── Models/ objetos que representam os dados │ └── Middleware/ código que roda antes/depois dos controllers ├── bootstrap/ │ └── app.php monta a aplicação: container, middlewares e rotas ├── routes/ │ └── api.php todas as rotas em um só lugar ├── public/ │ └── index.php única porta de entrada (raiz do servidor web) ├── storage/ banco de tokens e chaves (criado automaticamente) ├── vendor/ criado pelo Composer, não mexa ├── .env segredos e configurações (não versionar) ├── .gitignore └── composer.json

Como uma requisição percorre as pastas

Entender esse caminho ajuda a saber onde colocar cada pedaço de código:

  1. public/index.php recebe a requisição e carrega bootstrap/app.php.
  2. O Haki procura a rota em routes/api.php.
  3. Os middlewares rodam (CORS, autenticação, perfil...).
  4. O controller lê os dados da requisição e chama um service.
  5. O service aplica a regra de negócio e usa um repository para buscar ou salvar dados.
  6. O controller devolve o resultado, e o Haki transforma em JSON.
Regra prática

Controller não acessa banco. Service não conhece HTTP. Repository não tem regra de negócio. Se um arquivo começar a fazer duas dessas coisas, ele está na pasta errada.

public/index.php

A única porta de entrada. Ele só carrega a aplicação e a executa:

public/index.php
<?php

declare(strict_types=1);

// Única porta de entrada da API. Rode com: php -S localhost:8000 -t public

bootstrap/app.php

É aqui que a aplicação é montada: ligações do container, middlewares globais e rotas. Ele é separado do index.php para que os testes possam carregar a aplicação sem subir um servidor.

bootstrap/app.php
<?php

declare(strict_types=1);

use Haki\Haki;

require __DIR__ . '/../vendor/autoload.php';

$app = new Haki(dirname(__DIR__));

// Interfaces de app/Contracts são ligadas sozinhas às classes de app/Repositories pelo nome:
// ProdutoRepositoryInterface → ProdutoRepository ou PdoProdutoRepository.
$app->container()->discover('App\\Contracts', 'App\\Repositories');

// Exige tipos em todo o código do projeto (veja a página Tipagem).
$app->requireTypes();

// Para casos fora do padrão, ligue manualmente:
// $app->container()->bind(PagamentoInterface::class, StripePagamento::class);

// Middlewares globais, por exemplo:
// $app->middleware(Cors::class);

// Rotas
$app->routes(__DIR__ . '/../routes/api.php');

return $app;

routes/api.php

Todas as rotas ficam aqui. O projeto começa com uma só, que aponta para o controller de exemplo. As rotas ficam soltas no arquivo, sem função em volta:

routes/api.php
<?php

declare(strict_types=1);

use App\Controllers\HomeController;

/** @var Haki\Haki $app */

$app->get('/', [HomeController::class, 'index']);
De onde vem o $app?

O $app é criado em bootstrap/app.php com new Haki(...). A linha $app->routes(...) carrega este arquivo e entrega a ele essa mesma variável. A linha /** @var Haki\Haki $app */ não executa nada: só avisa o editor qual é o tipo, para ele completar os métodos.

Para separar as rotas em mais de um arquivo, carregue cada um no bootstrap:

bootstrap/app.php
$app->routes(__DIR__ . '/../routes/api.php');
$app->routes(__DIR__ . '/../routes/admin.php');

app/Controllers/HomeController.php

app/Controllers/HomeController.php
<?php

declare(strict_types=1);

namespace App\Controllers;

use Haki\Http\Request;
use Haki\Http\Response;

final class HomeController
{
    public function index(Request $request, Response $response): Response
    {
        return $response->json([
            'mensagem' => 'Bem-vindo ao Haki!',
            'caminho' => $request->path(),
        ]);
    }
}

Configuração

O arquivo .env

Algumas configurações mudam entre o seu computador e o servidor: a senha do banco, o modo de erro, o segredo do login. Em vez de escrever esses valores no código, eles ficam em um arquivo chamado .env, na raiz do projeto.

Cada linha é um par NOME=valor. Linhas começando com # são comentários:

.env
APP_ENV=development

# Gere com: php vendor/bin/haki key:generate
JWT_SECRET=a3f9c2...

# Variáveis da sua aplicação também podem ficar aqui
DB_HOST=localhost
DB_NAME=minha_api

O Haki lê esse arquivo sozinho quando você cria a aplicação com new Haki(dirname(__DIR__)). Você não precisa instalar nada para isso.

Regras do arquivo

  • Sem espaços em volta do =: APP_ENV=development.
  • Valores com espaço vão entre aspas: APP_NAME="Minha API".
  • Um comentário pode vir no fim da linha: JWT_TTL=900 # 15 minutos.
  • Se a mesma variável já existir no servidor (definida no Docker, na hospedagem ou pelo vlucas/phpdotenv), o valor do servidor vale e o .env é ignorado para ela.
Nunca envie o .env para o Git

Ele guarda segredos. O haki init já cria um .gitignore que o deixa de fora, e um .env.example: uma cópia com as mesmas chaves, mas sem os valores secretos, para mostrar ao time o que precisa ser preenchido. Quem clonar o projeto copia o exemplo e preenche: cp .env.example .env.

Os argumentos de new Haki()

A aplicação é criada no bootstrap/app.php:

$app = new Haki(dirname(__DIR__));               // raiz do projeto; o modo vem do APP_ENV
$app = new Haki(dirname(__DIR__), debug: true);  // força o modo de desenvolvimento
$app = new Haki(dirname(__DIR__), debug: false); // força o modo de produção

O primeiro argumento é a pasta raiz do projeto, onde o Haki procura o .env e a pasta storage/. Em bootstrap/app.php, __DIR__ vale a pasta bootstrap/, e dirname(__DIR__) sobe um nível até a raiz:

__DIR__             →  C:\projetos\minha-api\bootstrap
dirname(__DIR__)    →  C:\projetos\minha-api

Para consultar esses valores depois:

$app->basePath();              // 'C:\projetos\minha-api'
$app->basePath('storage/x');   // 'C:\projetos\minha-api\storage\x'
$app->isDebug();               // true em desenvolvimento

Rotas

Rotas básicas

Uma rota liga um método HTTP e um caminho a um código que responde. O Haki aceita os cinco métodos usados em APIs REST:

routes/api.php
$app->get('/produtos', [ProdutoController::class, 'index']);         // listar
$app->post('/produtos', [ProdutoController::class, 'store']);        // criar
$app->get('/produtos/{id}', [ProdutoController::class, 'show']);     // ver um
$app->put('/produtos/{id}', [ProdutoController::class, 'update']);   // substituir
$app->patch('/produtos/{id}', [ProdutoController::class, 'patch']);  // alterar parte
$app->delete('/produtos/{id}', [ProdutoController::class, 'destroy']); // remover

Closures ou controllers?

Para algo muito curto, uma função anônima resolve:

$app->get('/status', function () {
    return ['ok' => true];
});

Para todo o resto, use controllers. Eles deixam o arquivo de rotas legível e o código reutilizável. Use o formato [Classe::class, 'metodo'].

Todos os formatos de handler

O segundo argumento da rota (o handler) pode ser:

FormatoExemplo
Controller e método[ProdutoController::class, 'index']
Função anônimafunction (Request $request) { ... }
Classe invocável (um método __invoke)MostrarStatus::class

A classe invocável é útil para controllers de uma ação só:

app/Controllers/MostrarStatus.php
final class MostrarStatus
{
    public function __invoke(): array
    {
        return ['status' => 'online'];
    }
}

// routes/api.php
$app->get('/status', MostrarStatus::class);

Em todos os formatos, os parâmetros são injetados automaticamente.

Parâmetros na URL

Trechos entre chaves viram parâmetros. O valor chega no método pelo mesmo nome:

$app->get('/usuarios/{id}/pedidos/{pedido}', function (int $id, int $pedido) {
    return ['usuario' => $id, 'pedido' => $pedido];
});

Se você tipar o parâmetro como int, o Haki converte o valor. Se alguém acessar /usuarios/abc/pedidos/1, a resposta é 404 automaticamente, e o seu código nem chega a rodar.

Atenção

Parâmetros vêm da URL, ou seja, do usuário. Valide sempre se o recurso existe e se a pessoa pode acessá-lo.

Grupos de rotas

Grupos aplicam um prefixo e regras em comum a várias rotas de uma vez:

$app->group('/admin', function (Haki $app) {
    $app->get('/usuarios', [AdminController::class, 'usuarios']);   // /admin/usuarios
    $app->get('/relatorios', [AdminController::class, 'relatorios']); // /admin/relatorios
})->role('admin');

Grupos podem ser aninhados, e um grupo aceita ->auth(), ->role() e ->middleware(), exatamente como uma rota.

Detalhes que o Haki resolve

  • /produtos/ e /produtos são a mesma rota.
  • A query string (?pagina=2) não interfere na rota.
  • Rotas fixas têm prioridade: /usuarios/novo vence /usuarios/{id}.

Controllers

O que é um controller

Um controller é a classe que atende uma rota. Pense nele como o atendente de uma loja: recebe o pedido (a requisição), chama quem sabe resolver (os services e repositories) e entrega a resposta. Ele não deve fazer o trabalho pesado sozinho.

Cada método público do controller pode responder a uma rota. O normal é ter um controller por recurso da API: ProdutoController para produtos, ClienteController para clientes, e assim por diante.

Criando um controller passo a passo

  1. Crie o arquivo em app/Controllers

    O nome do arquivo é o nome da classe: ProdutoController.php.

    app/Controllers/ProdutoController.php
    <?php

declare(strict_types=1);

namespace App\Controllers;

use Haki\Http\Request;

final class ProdutoController
{
    public function index(Request $request): array
    {
        $pagina = (int) $request->query('pagina', 1);

        return ['pagina' => $pagina, 'produtos' => []];
    }

    public function show(int $id): array
    {
        return ['produto' => ['id' => $id]];
    }
}

    O namespace App\Controllers; precisa bater com a pasta. É assim que o Composer encontra a classe.

  2. Registre as rotas
    routes/api.php
    use App\Controllers\ProdutoController;

/** @var Haki\Haki $app */

$app->get('/produtos', [ProdutoController::class, 'index']);
$app->get('/produtos/{id}', [ProdutoController::class, 'show']);

    [ProdutoController::class, 'index'] quer dizer: "nessa rota, chame o método index da classe ProdutoController".

  3. Teste 
    curl http://localhost:8000/produtos/5
    { "produto": { "id": 5 } }

Requisições

O objeto Request

Tudo o que o cliente envia (URL, parâmetros, corpo, cabeçalhos e token) chega no objeto Request. Para usá-lo, basta pedir um parâmetro do tipo Request no método do controller ou na função da rota. O Haki entrega a requisição atual.

app/Controllers/ProdutoController.php
use Haki\Http\Request;

final class ProdutoController
{
    public function index(Request $request): array
    {
        return ['busca' => $request->query('busca')];
    }
}

Funciona da mesma forma em uma função anônima:

$app->get('/produtos', function (Request $request) {
    return ['busca' => $request->query('busca')];
});

As três origens de dados

Os dados de uma requisição podem vir de três lugares diferentes, e cada um tem o seu método. Veja uma requisição completa:

requisição HTTP
PUT /produtos/10?notificar=sim HTTP/1.1
Content-Type: application/json
Authorization: Bearer eyJhbGciOi...

{"nome": "Chapéu de palha", "preco": 49.9}

Com a rota $app->put('/produtos/{id}', ...), cada pedaço é lido assim:

PedaçoOnde estáMétodoResultado
Parâmetro de rotaCaminho: /produtos/10param('id')'10'
Query stringDepois do ?: notificar=simquery('notificar')'sim'
CorpoJSON depois dos cabeçalhosinput('nome')'Chapéu de palha'
CabeçalhoContent-Type: ...header('Content-Type')'application/json'
TokenAuthorization: Bearer ...bearerToken()'eyJhbGciOi...'
Quando usar cada um

Parâmetro de rota identifica qual recurso: /produtos/10. Query string filtra, busca, ordena e pagina, normalmente em GET: /produtos?busca=espada&pagina=2. Corpo traz os dados para criar ou alterar algo, em POST, PUT e PATCH.

Query string: query()

A query string é tudo o que vem depois do ? na URL, no formato chave=valor, separado por &.

http://localhost:8000/produtos?busca=espada&pagina=2
                               └──── query string ────┘
$request->query();                 // todos: ['busca' => 'espada', 'pagina' => '2']
$request->query('busca');          // um só: 'espada'
$request->query('ordem');          // não veio na URL: null
$request->query('pagina', 1);      // com valor padrão: '2' (ou 1, se não vier)

Os valores chegam como texto

Tudo o que vem da URL é texto. pagina=2 chega como a string '2', não como o número 2. Converta antes de fazer contas ou comparações:

$pagina = (int) $request->query('pagina', 1);
$porPagina = min((int) $request->query('limite', 20), 100); // nunca mais que 100
$ativos = $request->query('ativos') === 'true';

Listas na query string

Use colchetes no nome para enviar vários valores:

// GET /produtos?tags[]=php&tags[]=api&preco[min]=10&preco[max]=50

$request->query('tags');   // ['php', 'api']
$request->query('preco');  // ['min' => '10', 'max' => '50']

Exemplo: busca com paginação

public function index(Request $request): array
{
    $busca = trim((string) $request->query('busca', ''));
    $pagina = max(1, (int) $request->query('pagina', 1));

    $produtos = $this->produtos->buscar($busca, $pagina);

    return ['pagina' => $pagina, 'produtos' => $produtos];
}

Parâmetros de rota: param()

Parâmetros de rota são os trechos entre chaves no caminho. Há duas formas de ler o valor.

Como argumento do método (recomendado)

Declare um argumento com o mesmo nome do parâmetro. Se você tipar o argumento, o Haki converte o valor:

$app->get('/produtos/{id}', [ProdutoController::class, 'show']);

public function show(int $id): array   // '10' vira o número 10
{
    return ['id' => $id];
}

$request->param('id');          // '10' (sempre texto)

Corpo da requisição: input()

O corpo é onde o cliente envia os dados em POST, PUT e PATCH. O Haki entende dois formatos automaticamente:

  • JSON, quando o cabeçalho é Content-Type: application/json. É o formato usado por APIs, apps e fetch().
  • Formulário, quando vem de um <form> HTML comum.
corpo enviado
{
  "nome": "Nami",
  "idade": 20,
  "endereco": { "cidade": "Cocoyashi", "pais": "East Blue" },
  "tags": ["navegadora", "cartógrafa"]
}
$request->input('nome');              // 'Nami'
$request->input('idade');             // 20 (no JSON, números chegam como número)
$request->input('endereco.cidade');   // 'Cocoyashi' (ponto acessa campos internos)
$request->input('tags');              // ['navegadora', 'cartógrafa']
$request->input('telefone');          // null (não foi enviado)
$request->input('telefone', '-');     // '-' (valor padrão)

$request->has('endereco.pais');       // true
$request->all();                      // o corpo inteiro como array
$request->only(['nome', 'idade']);    // ['nome' => 'Nami', 'idade' => 20]
$request->body();                     // o corpo cru, como texto
Atenção

Use only() para pegar só os campos esperados. Passar all() direto para o banco permite que alguém envie campos extras, como "perfil": "admin", e altere o que não devia.

JSON inválido

Se o cliente enviar Content-Type: application/json com um corpo quebrado, a primeira leitura (input(), all(), has() ou only()) responde 400 com "JSON inválido no corpo da requisição". Você não precisa tratar isso.

Enviando um corpo JSON (cliente)

curl -X POST http://localhost:8000/clientes \
     -H "Content-Type: application/json" \
     -d '{"nome": "Nami", "idade": 20}'
JavaScript
await fetch('http://localhost:8000/clientes', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ nome: 'Nami', idade: 20 }),
});

Cabeçalhos e token

$request->header('Accept');            // 'application/json'
$request->header('accept');            // o mesmo: o nome não diferencia maiúsculas
$request->header('X-Versao', '1');     // com valor padrão
$request->headers();                   // todos, com nomes em minúsculas
$request->isJson();                    // true se o Content-Type for JSON
$request->bearerToken();               // token de "Authorization: Bearer ..." ou null

Na maioria dos casos você não precisa de bearerToken(): o ->auth() lê e valida o token sozinho. Ele é útil para casos especiais, como validar o token manualmente com $auth->authenticate().

Informações da requisição

// GET /produtos/10?ordem=preco

$request->path();     // '/produtos/10' (sem query string e sem barra final)
$request->uri();      // '/produtos/10?ordem=preco' (como chegou)
$request->ip();       // '127.0.0.1'

Validando o que chega

Tudo o que vem da requisição deve ser tratado como não confiável. Em vez de conferir campo por campo com if, descreva as regras e deixe o Haki validar e converter os tipos:

$dados = $request->validate(function (Rule $rule) {
    return [
        'nome'  => $rule->text()->length(3, 100),
        'email' => $rule->email(),
    ];
});

Validação

Visão geral

Validar é conferir se os dados enviados pelo cliente estão certos antes de usá-los. No Haki, você descreve cada campo com $rule, e o framework confere, converte os tipos e responde com mensagens em português quando algo está errado.

'nome'  => $rule->text()->length(3, 100),     // texto de 3 a 100 caracteres
'email' => $rule->email(),                     // e-mail válido
'idade' => $rule->integer()->min(18)->optional(), // inteiro, 18 ou mais, pode faltar

Há duas formas de validar:

  • Classe de validação (FormRequest): o jeito recomendado. Deixa o controller limpo e a regra reaproveitável.
  • $request->validate(): um atalho para casos rápidos, direto no controller.

Criando uma classe de validação

  1. Gere a classe 
    php vendor/bin/haki make:request CriarClienteRequest

    O arquivo é criado em app/Requests/CriarClienteRequest.php.

  2. Descreva os campos em rules()
    app/Requests/CriarClienteRequest.php
    <?php

declare(strict_types=1);

namespace App\Requests;

use Haki\Validation\FormRequest;
use Haki\Validation\Rule;

final class CriarClienteRequest extends FormRequest
{
    public function rules(Rule $rule): array
    {
        return [
            'nome'  => $rule->text()->length(3, 100),
            'email' => $rule->email(),
            'idade' => $rule->integer()->min(18)->optional(),

            'endereco' => [
                'cidade' => $rule->text(),
                'cep'    => $rule->text()->pattern('/^\d{5}-?\d{3}$/'),
            ],

            'tags' => $rule->list($rule->oneOf('vip', 'novo')),
        ];
    }
}
  3. Peça a classe no controller
    app/Controllers/ClienteController.php
    use App\Requests\CriarClienteRequest;

public function store(CriarClienteRequest $request, Response $response): Response
{
    $cliente = $this->clientes->criar($request->validated());

    return $response->json(['cliente' => $cliente], 201);
}

    Pronto. O Haki valida antes do controller rodar. Se algo estiver errado, o controller nem é chamado.

O que o cliente recebe

Com dados inválidos, a resposta é 422, com as mensagens separadas por campo:

{
  "erro": "Dados inválidos",
  "status": 422,
  "campos": {
    "nome": ["O campo nome precisa ter entre 3 e 100 caracteres."],
    "email": ["O campo email precisa ser um e-mail válido."],
    "endereco.cep": ["O campo cep está em um formato inválido."],
    "tags.1": ["O item 2 de tags precisa ser um destes: vip, novo."]
  }

Campos dentro de objetos usam ponto (endereco.cep), e itens de lista usam a posição, começando em zero (tags.1 é o segundo item). No front-end, mostre cada mensagem embaixo do campo correspondente.

'ativo'   => $rule->boolean()->optional(true),  // se faltar: true

Formats::uf('mg');                   // 'MG'

length conta tamanho (letras de um texto, itens de uma lista). min e max comparam o valor de um número. Uma senha de pelo menos 8 caracteres é text()->length(8); uma idade de pelo menos 18 anos é integer()->min(18).

Objetos e listas

Objetos (um grupo de campos dentro de outro)

Use quando o cliente envia um objeto dentro de outro no JSON. A regra simplesmente copia o formato do JSON que chega. Imagine que o front-end envia este cadastro:

JSON enviado
{
  "nome": "Nami",
  "endereco": {
    "rua": "Rua das Laranjas",
    "numero": 42,
    "cidade": "Cocoyashi"
  }
}

Repare que endereco não é um texto: é um grupo de campos entre { }. Por isso a regra também é um grupo, entre [ ]:

rules()
return [
    'nome' => $rule->text(),

    'endereco' => [                    // "endereco" é um objeto com estes campos:
        'rua'    => $rule->text(),     //    endereco.rua    precisa ser texto
        'numero' => $rule->integer(),  //    endereco.numero precisa ser inteiro
        'cidade' => $rule->text(),     //    endereco.cidade precisa ser texto
    ],
];

Lendo em português: "endereco é obrigatório e precisa ter rua (texto), numero (inteiro) e cidade (texto)." Veja como os dois têm o mesmo formato:

JSON                          Regra
{                             [
  "nome": "Nami",               'nome' => $rule->text(),
  "endereco": {                 'endereco' => [
    "rua": "...",                   'rua'    => $rule->text(),
    "numero": 42,                   'numero' => $rule->integer(),
    "cidade": "..."                 'cidade' => $rule->text(),
  }                             ],
}                             ]

Pegando os valores do objeto

$request->get('endereco.cidade');   // 'Cocoyashi' (o ponto entra dentro do objeto)
$request->endereco;                 // ['rua' => '...', 'numero' => 42, 'cidade' => 'Cocoyashi']
$request->endereco['numero'];       // 42 (já convertido para inteiro)

Como os erros aparecem

Se o cliente mandar o endereço sem a cidade e com o número errado:

{ "nome": "Nami", "endereco": { "rua": "Rua das Laranjas", "numero": "abc" } }

A resposta usa o ponto para mostrar onde está o erro:

"campos": {
  "endereco.numero": ["O campo numero precisa ser um número inteiro."],
  "endereco.cidade": ["O campo cidade é obrigatório."]
}

E se o cliente não mandar o endereco inteiro:

"campos": { "endereco": ["O campo endereco é obrigatório."] }

Quando você não precisa de objeto

Se o seu front-end envia os campos soltos, sem agrupar:

{ "nome": "Nami", "rua": "Rua das Laranjas", "numero": 42, "cidade": "Cocoyashi" }

então as regras também ficam soltas, sem o array em volta:

return [
    'nome'   => $rule->text(),
    'rua'    => $rule->text(),
    'numero' => $rule->integer(),
    'cidade' => $rule->text(),
];
Regra prática

Use o array interno só quando o JSON também tiver um objeto interno. Os dois formatos funcionam; escolha o que combina com o que o seu front-end envia.

Objeto opcional

Um array dentro das regras é sempre obrigatório. Para um objeto que pode faltar, use $rule->object() com optional():

'endereco' => $rule->object([
    'rua'    => $rule->text(),
    'numero' => $rule->integer(),
    'cidade' => $rule->text(),
])->optional(),   // se não vier, endereco fica null

// Lista de objetos (itens de um pedido)

Mensagens e nomes dos campos

As mensagens usam o nome do campo. Para trocar por um nome mais amigável, defina labels():

public function labels(): array
{
    return [
        'email'        => 'e-mail',
        'endereco.cep' => 'CEP',
    ];
}
// "O campo e-mail precisa ser um e-mail válido."

Para trocar a mensagem inteira de uma regra, use o segundo argumento de pattern() e check(), ou message() para o campo todo:

'cep' => $rule->text()->pattern('/^\d{5}-?\d{3}$/', 'Informe um CEP como 12345-678.'),
'apelido' => $rule->text()->length(3, 20)->message('O apelido precisa ter de 3 a 20 letras.'),

Preparando os dados: prepare()

prepare() roda antes da validação. Use para limpar os dados, como tirar a máscara de um CPF:

protected function prepare(array $data): array
{
    $data['cpf'] = preg_replace('/\D/', '', (string) ($data['cpf'] ?? '')); // "123.456.789-01" → "12345678901"
    $data['email'] = strtolower((string) ($data['email'] ?? ''));

    return $data;
}

Regras com lógica própria

check() em um campo

Para uma regra que não existe pronta, passe uma função que recebe o valor (já convertido) e retorna true se estiver certo:

'cpf' => $rule->text()->check(function (string $cpf): bool {
    return Cpf::valido($cpf);
}, 'Informe um CPF válido.'),

check() na classe

Para regras que dependem do banco ou de vários campos, sobrescreva check(). Ele roda depois que todas as regras de rules() passaram e recebe os dados validados. Use $this->fail() para marcar um erro. A classe recebe dependências pelo construtor, como um controller:

final class CriarClienteRequest extends FormRequest
{
    public function __construct(private readonly ClienteRepositoryInterface $clientes)
    {
    }

    public function rules(Rule $rule): array
    {
        return [
            'email'       => $rule->email(),
            'data_inicio' => $rule->date(),
            'data_fim'    => $rule->date(),
        ];
    }

    protected function check(array $data): void
    {
        if ($this->clientes->emailExiste($data['email'])) {
            $this->fail('email', 'Este e-mail já está cadastrado.');
        }

        if ($data['data_fim'] < $data['data_inicio']) {
            $this->fail('data_fim', 'A data final precisa ser depois da inicial.');
        }
    }
}

Validação rápida: $request->validate()

Para poucos campos, valide direto no controller, sem criar uma classe:

use Haki\Validation\Rule;

{
    $dados = $request->validate(function (Rule $rule) {
        return [
            'email' => $rule->email(),
            'senha' => $rule->text()->length(8),
        ];
    });

    // $dados = ['email' => '...', 'senha' => '...']
}

O comportamento é o mesmo: resposta 422 automática e dados convertidos. O segundo argumento opcional define os nomes amigáveis: $request->validate(..., ['email' => 'e-mail']).

Validando a query string

As regras valem para a query string e para o corpo juntos (se o mesmo campo vier nos dois, vale o do corpo). Assim, a mesma técnica serve para filtros de listagem:

// GET /produtos?busca=espada&pagina=2
public function rules(Rule $rule): array
{
    return [
        'busca'  => $rule->text()->length(2)->optional(),
        'pagina' => $rule->integer()->min(1)->optional(1),
        'ordem'  => $rule->oneOf('nome', 'preco')->optional('nome'),
    ];
}

Em que momento a validação roda

  1. Middlewares, autenticação (->auth()) e perfil (->role()).
  2. prepare() ajusta os dados.
  3. As regras de rules() são aplicadas.
  4. Se passaram, check() roda.
  5. Se tudo deu certo, o controller é chamado.

Por isso uma requisição sem token recebe 401, e não 422: a autenticação vem antes.

Banco de dados

Como o Haki trabalha com banco

O Haki não tem banco de dados embutido nem ORM. Você usa o PDO, que já vem no PHP, organizado em quatro peças, cada uma com uma responsabilidade.

PeçaOndeResponsabilidade
Conexãoapp/Database/Connection.phpLê o .env e abre a conexão
Modelapp/Models/Representa um registro (um produto, um cliente)
Interfaceapp/Contracts/Diz o que dá para fazer com os registros
Repositoryapp/Repositories/Faz o SQL de verdade
 
Controller ──▶ ProdutoRepositoryInterface ──▶ PdoProdutoRepository ──▶ Connection ──▶ banco
                                                      │

O controller nunca escreve SQL: ele pede a interface e recebe models prontas. Assim, todo o SQL fica num lugar só, e trocar de banco ou testar sem banco não exige mexer no controller.

2. A classe de conexão

Uma classe pequena que lê as variáveis DB_* e entrega o PDO. A conexão só é aberta na primeira vez que alguém precisa dela:

app/Database/Connection.php
<?php

declare(strict_types=1);

namespace App\Database;

use Haki\Support\Env;
use PDO;
use RuntimeException;

final class Connection
{
    private ?PDO $pdo = null;

    public function __construct(
        private readonly string $driver,
        private readonly string $database,
        private readonly string $host = '127.0.0.1',
        private readonly int $port = 3306,
        private readonly ?string $username = null,
        #[\SensitiveParameter] private readonly ?string $password = null,
    ) {
    }

    public static function fromEnv(string $basePath): self
    {
        $driver = (string) Env::get('DB_CONNECTION', 'sqlite');
        $database = (string) Env::get('DB_DATABASE', 'database/app.sqlite');

        // No SQLite, um caminho relativo é a partir da raiz do projeto.
        if ($driver === 'sqlite' && !preg_match('#^([A-Za-z]:[\\\\/]|/)#', $database)) {
            $database = rtrim($basePath, '/\\') . DIRECTORY_SEPARATOR . $database;
        }

        return new self(
            $driver,
            $database,
            (string) Env::get('DB_HOST', '127.0.0.1'),
            (int) Env::get('DB_PORT', 3306),
            Env::get('DB_USERNAME'),
            Env::get('DB_PASSWORD'),
        );
    }

    public function pdo(): PDO
    {
        return $this->pdo ??= $this->connect();
    }

    private function connect(): PDO
    {
        $options = [
            PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION,       // erro de SQL vira exceção
            PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,  // linhas como array associativo
        ];

        return match ($this->driver) {
            'sqlite' => new PDO('sqlite:' . $this->database, null, null, $options),
            'mysql' => new PDO(
                "mysql:host={$this->host};port={$this->port};dbname={$this->database};charset=utf8mb4",
                $this->username,
                $this->password,
                $options,
            ),
            default => throw new RuntimeException("DB_CONNECTION \"{$this->driver}\" não suportado. Use sqlite ou mysql."),
        };
    }
}

6. O repository: onde fica o SQL

O nome PdoProdutoRepository segue o padrão do discover(), então o Haki o liga à interface sem nenhum bind:

app/Repositories/PdoProdutoRepository.php
<?php

declare(strict_types=1);

namespace App\Repositories;

use App\Contracts\ProdutoRepositoryInterface;
use App\Database\Connection;
use App\Models\Produto;
use PDO;

final class PdoProdutoRepository implements ProdutoRepositoryInterface
{
    private readonly PDO $pdo;

    public function __construct(Connection $connection)
    {
        $this->pdo = $connection->pdo();
    }

    public function listar(int $pagina, int $porPagina): array
    {
        $stmt = $this->pdo->prepare('SELECT * FROM produtos ORDER BY id LIMIT :limite OFFSET :inicio');
        $stmt->bindValue(':limite', $porPagina, PDO::PARAM_INT);
        $stmt->bindValue(':inicio', ($pagina - 1) * $porPagina, PDO::PARAM_INT);
        $stmt->execute();

        $produtos = [];

        foreach ($stmt->fetchAll() as $linha) {
            $produtos[] = new Produto((int) $linha['id'], $linha['nome'], (float) $linha['preco'], (int) $linha['estoque']);
        }

        return $produtos;
    }

    public function buscar(int $id): ?Produto
    {
        $stmt = $this->pdo->prepare('SELECT * FROM produtos WHERE id = ?');
        $stmt->execute([$id]);
        $linha = $stmt->fetch();

        if (!$linha) {
            return null;
        }

        return new Produto((int) $linha['id'], $linha['nome'], (float) $linha['preco'], (int) $linha['estoque']);
    }

    public function criar(string $nome, float $preco, int $estoque): Produto
    {
        $stmt = $this->pdo->prepare('INSERT INTO produtos (nome, preco, estoque) VALUES (?, ?, ?)');
        $stmt->execute([$nome, $preco, $estoque]);

        return new Produto((int) $this->pdo->lastInsertId(), $nome, $preco, $estoque);
    }

    public function atualizar(int $id, string $nome, float $preco, int $estoque): void
    {
        $stmt = $this->pdo->prepare('UPDATE produtos SET nome = ?, preco = ?, estoque = ? WHERE id = ?');
        $stmt->execute([$nome, $preco, $estoque, $id]);
    }

    public function apagar(int $id): bool
    {
        $stmt = $this->pdo->prepare('DELETE FROM produtos WHERE id = ?');
        $stmt->execute([$id]);

        return $stmt->rowCount() > 0;
    }
}

$pdo->prepare('... WHERE id = ?')Prepara o SQL com lugares (?) para os valores

Nunca coloque valores direto no SQL

Esta é a regra mais importante desta página. Colocar uma variável dentro do texto do SQL permite que alguém mande um "valor" que é, na verdade, outro comando. Isso se chama SQL injection:

// ERRADO: se $busca for  ' OR 1=1 --  a consulta devolve tudo; com outros textos, pode apagar dados
$pdo->query("SELECT * FROM produtos WHERE nome = '$busca'");

// CERTO: o valor vai separado do SQL e nunca é interpretado como comando
$stmt = $pdo->prepare('SELECT * FROM produtos WHERE nome = ?');
$stmt->execute([$busca]);

Use sempre prepare() com ? (ou :nome) para qualquer valor que venha de fora. A única exceção são partes fixas que você mesmo escreveu, como o nome de uma coluna escolhida de uma lista permitida:

$ordem = in_array($request->query('ordem'), ['nome', 'preco'], true) ? $request->query('ordem') : 'id';
$stmt = $pdo->prepare("SELECT * FROM produtos ORDER BY $ordem");   // seguro: só valores da lista

Paginação

Nunca devolva uma tabela inteira: com milhares de linhas, a API fica lenta. Use LIMIT e OFFSET:

página 1, 20 por página  →  LIMIT 20 OFFSET 0
página 2, 20 por página  →  LIMIT 20 OFFSET 20
página 3, 20 por página  →  LIMIT 20 OFFSET 40

Como no listar() acima, passe LIMIT e OFFSET com bindValue(..., PDO::PARAM_INT). Se forem como texto, o MySQL recusa a consulta.

Transações: tudo ou nada

Quando várias gravações dependem umas das outras (criar um pedido e os itens dele), use uma transação. Se qualquer uma falhar, nada é gravado:

public function criarPedido(int $clienteId, array $itens): int
{
    $this->pdo->beginTransaction();

    try {
        $this->pdo->prepare('INSERT INTO pedidos (cliente_id) VALUES (?)')->execute([$clienteId]);
        $pedidoId = (int) $this->pdo->lastInsertId();

        $item = $this->pdo->prepare('INSERT INTO itens (pedido_id, produto_id, quantidade) VALUES (?, ?, ?)');

        foreach ($itens as $i) {
            $item->execute([$pedidoId, $i['produto_id'], $i['quantidade']]);
        }

        $this->pdo->commit();      // grava tudo

        return $pedidoId;
    } catch (Throwable $e) {
        $this->pdo->rollBack();    // desfaz tudo
        throw $e;
    }
}

As partes de uma resposta

Toda resposta HTTP tem três partes:

});

// 204 sem conteúdo (comum depois de apagar algo)
$app->delete('/produto/{id}', function (int $id) {
    return null;
});

O JSON sai com acentos e barras legíveis ("Olá", e não "Olá").

Controlando status e cabeçalhos

Quando precisar de outro status ou de cabeçalhos, peça um Response no método e monte a resposta:

public function store(CriarProdutoRequest $request, Response $response): Response

    return $response
        ->header('Location', '/produtos/' . $produto->id)   // onde o recurso novo está
        ->json(['produto' => $produto], 201);                 // 201 = criado

Quando a resposta é enviada?

Os métodos de Response só montam a resposta e devolvem o próprio objeto (por isso dá para encadear ->header()->json()). Quem envia para o cliente é o $app->run(), uma única vez, depois que todos os middlewares terminam. Isso permite que um middleware adicione cabeçalhos à resposta do controller.

Por isso, sempre retorne a resposta:

return $response->json($dados);   // certo
$response->json($dados);          // errado: a resposta montada é descartada e o cliente recebe 204

Objetos no JSON e campos escondidos

Um objeto retornado vira JSON a partir das suas propriedades públicas. Isso pode vazar o que não devia, como o hash da senha. Para controlar exatamente o que sai, implemente JsonSerializable:

app/Models/Usuario.php
final class Usuario implements JsonSerializable
{
    public function __construct(
        public readonly int $id,
        public readonly string $nome,
        public readonly string $senhaHash,
    ) {
    }

    public function jsonSerialize(): array
    {
        return ['id' => $this->id, 'nome' => $this->nome];   // senhaHash fica de fora
    }
}

Agora, return ['usuario' => $usuario]; devolve só {"usuario": {"id": 1, "nome": "Nami"}}.

Quando o JSON não pode ser gerado

Se os dados tiverem algo que não vira JSON (um texto com codificação quebrada, por exemplo), a resposta vira um erro 500. Em desenvolvimento, a dica explica o motivo.

Middleware

O que é um middleware

Um middleware é um código que roda antes e/ou depois do controller, em várias rotas de uma vez. É o lugar certo para o que se repete: liberar o acesso do front-end (CORS), registrar acessos, exigir uma chave de API, medir tempo, colocar a API em manutenção.

Pense em camadas de uma cebola. A requisição atravessa cada camada até chegar no controller, e a resposta volta pelo mesmo caminho, de dentro para fora:

requisição ──▶ [ CORS ] ──▶ [ Log ] ──▶ [ Auth ] ──▶  Controller
                                                            │
resposta   ◀── [ CORS ] ◀── [ Log ] ◀── [ Auth ] ◀──────────┘

Cada camada pode olhar a requisição, deixar passar, barrar ou alterar a resposta que volta.

Criando um middleware

Crie uma classe em app/Middleware que implemente MiddlewareInterface. Ela tem um único método, handle():

app/Middleware/MedirTempo.php
<?php

declare(strict_types=1);

namespace App\Middleware;

use Haki\Http\Request;
use Haki\Http\Response;
use Haki\Middleware\MiddlewareInterface;

final class MedirTempo implements MiddlewareInterface
{
    public function handle(Request $request, callable $next): Response
    {
        // 1. ANTES: roda antes do controller
        $inicio = microtime(true);

        // 2. Chama a próxima camada (outro middleware ou o controller)
        $response = $next($request);

        // 3. DEPOIS: roda com a resposta já pronta
        $ms = round((microtime(true) - $inicio) * 1000, 2);

        return $response->header('X-Tempo-Ms', (string) $ms);
    }
}

O segredo é o $next($request): tudo o que vem antes dele roda antes do controller, e tudo o que vem depois roda depois. O handle() sempre precisa retornar uma Response.

Onde aplicar

Há três lugares, do mais amplo ao mais específico:

// 1. Global: todas as requisições (em bootstrap/app.php)
$app->middleware(MedirTempo::class);

// 2. Em um grupo de rotas (em routes/api.php)
$app->group('/api', function (Haki $app) {
    $app->get('/produtos', [ProdutoController::class, 'index']);
})->middleware(RegistrarAcesso::class);

// 3. Em uma rota só
$app->post('/upload', [UploadController::class, 'store'])->middleware(ExigirChaveApi::class);

Você pode passar o middleware de três formas:

Instâncianew Cors('https://meusite.com')Quando o construtor precisa de um valor (texto, número).
Função anônimafunction (Request $request, callable $next) { ... }Algo bem curto, usado em um lugar só.

Ordem de execução

A ordem é sempre a mesma:

  1. Middlewares globais, na ordem em que foram registrados
  2. Middlewares do grupo
  3. Autenticação (->auth())
  4. Perfil (->role())
  5. Middlewares da rota
  6. Validação (se o controller pedir uma classe de validação) e o controller

Consequências práticas: quando um middleware de rota roda, $request->user() já está preenchido. E middlewares globais rodam até em respostas de erro (404, 401, 422...), o que é importante para o CORS.

Barrando a requisição

Para impedir que a requisição chegue no controller, retorne uma resposta sem chamar $next, ou lance uma HttpException:

app/Middleware/ExigirChaveApi.php
use Haki\Exceptions\HttpException;
use Haki\Support\Env;

final class ExigirChaveApi implements MiddlewareInterface
{
    public function handle(Request $request, callable $next): Response
    {
        $esperada = Env::get('API_KEY');           // definida no .env
        $chave = $request->header('X-Api-Key');    // enviada pelo cliente

        if (!is_string($esperada) || $chave === null || !hash_equals($esperada, $chave)) {
            throw new HttpException(401, 'Chave de API inválida');
        }

        return $next($request);
    }
}
app/Middleware/ModoManutencao.php
final class ModoManutencao implements MiddlewareInterface
{
    public function handle(Request $request, callable $next): Response
    {
        if (file_exists(__DIR__ . '/../../storage/manutencao')) {
            return (new Response())
                ->header('Retry-After', '600')
                ->json(['erro' => 'Voltamos em instantes'], 503);

}

Para ligar a manutenção, basta criar o arquivo storage/manutencao; para desligar, apagar.

Exemplo: CORS

O navegador bloqueia um site de chamar uma API em outro endereço, a menos que a API autorize. Esse middleware autoriza o seu front-end:

app/Middleware/Cors.php
final class Cors implements MiddlewareInterface
{
    public function __construct(private readonly string $origem = 'http://localhost:5173')
    {
    }

    public function handle(Request $request, callable $next): Response
    {
        // Antes da requisição real, o navegador manda um OPTIONS perguntando se pode ("preflight").
        $response = $request->method() === 'OPTIONS' ? new Response('', 204) : $next($request);

        return $response
            ->header('Access-Control-Allow-Origin', $this->origem)
            ->header('Access-Control-Allow-Headers', 'Authorization, Content-Type')
            ->header('Access-Control-Allow-Methods', 'GET, POST, PUT, PATCH, DELETE, OPTIONS');
    }
}
bootstrap/app.php
$app->middleware(new Cors('https://meusite.com.br'));

Registre como global e como primeiro middleware. Assim, até as respostas de erro levam os cabeçalhos, e o navegador consegue mostrar a mensagem de erro em vez de um erro de CORS genérico.

Exemplo: registrando os acessos

app/Middleware/RegistrarAcesso.php
final class RegistrarAcesso implements MiddlewareInterface
{
    public function handle(Request $request, callable $next): Response
    {
        $response = $next($request);

        error_log(sprintf(
            '%s %s → %d (usuário %s, IP %s)',
            $request->method(),
            $request->path(),
            $response->getStatus(),
            $request->user()?->id ?? 'anônimo',
            $request->ip() ?? '?',
        ));

        return $response;
    }
}
Atenção

Nunca registre no log o token, a senha ou o corpo inteiro das requisições. Logs costumam ser lidos por mais pessoas e guardados por muito tempo.

Tratamento de erros

Formato padrão

Todo erro vira um JSON com o mesmo formato, então o front-end sempre sabe onde procurar a mensagem:

{ "erro": "Usuário não encontrado", "status": 404 }

Respondendo com um erro

Em qualquer lugar (controller, service, middleware), lance uma HttpException:

use Haki\Exceptions\HttpException;

$usuario = $this->usuarios->buscarPorId($id)
    ?? throw new HttpException(404, 'Usuário não encontrado');

if ($this->usuarios->emailExiste($email)) {
    throw new HttpException(409, 'Este e-mail já está cadastrado');
}

Mensagem padrão e cabeçalhos

A mensagem é opcional. Sem ela, o Haki usa uma mensagem padrão para o código:

throw new HttpException(404);   // { "erro": "Não encontrado", "status": 404 }
throw new HttpException(429);   // { "erro": "Muitas requisições", "status": 429 }

O terceiro argumento adiciona cabeçalhos à resposta de erro, e o quarto é uma dica que aparece só em desenvolvimento:

throw new HttpException(
    429,
    'Muitas tentativas. Tente de novo em 1 minuto',
    ['Retry-After' => '60'],
    'O IP ' . $request->ip() . ' passou do limite de 5 tentativas.',
);

Depuração com haki()

A função haki()

Depurar é descobrir o que está acontecendo dentro do código: qual valor uma variável tem, o que chegou na requisição, por que um if não entrou. A função global haki() mostra qualquer valor de forma organizada. Ela substitui o var_dump e o print_r, que são difíceis de ler.

haki($usuario);                         // um valor
haki($request->all(), $produtos, 123);  // vários de uma vez

Ela está disponível em qualquer lugar do projeto, sem use.

O que aparece

  • Onde foi chamada: o arquivo e a linha, para você achar e apagar depois.
  • O tipo de cada valor, com uma cor e uma etiqueta: string, int, float, bool, null, array, object, enum, closure.
  • Textos com a quantidade de caracteres.
  • Arrays com a quantidade de itens e se são lista ([0, 1, 2]) ou associativo (['nome' => ...]).
  • Objetos com a classe, um número de identificação e a visibilidade de cada propriedade: + pública, # protegida, - privada.
  • Datas já formatadas e closures com a assinatura e onde foram criadas.
  • Referências circulares (um objeto que aponta para si mesmo) são marcadas, em vez de travar a página.

Um cadastro está falhando e você não sabe por quê. Coloque um haki() no começo do método e chame a rota:

Na saída você vê, por exemplo, que o front-end mandou "Nome" com N maiúsculo, ou que o Content-Type não é application/json e por isso o corpo chegou vazio.

Para ver um valor e parar ali, sem rodar o resto do código, use exit logo depois:

haki($pedido);

haki() devolve o próprio valor recebido (ou um array, se receber vários). Assim, dá para usar no meio de uma expressão sem mudar o código:

$total = haki($this->calcularTotal($pedido));   // mostra o total e continua normalmente

Como funciona a autenticação

Visão geral

O Haki usa JSON Web Tokens (JWT). Depois do login, o cliente recebe um token e o envia em cada requisição protegida. O servidor confere a assinatura do token e sabe quem é o usuário sem guardar sessão.

O fluxo completo

  1. O cliente envia e-mail e senha para POST /login.
  2. A sua aplicação confere as credenciais (o Haki não sabe nada sobre senhas).
  3. Se estiverem corretas, você chama $auth->login($usuario->id).
  4. O Haki devolve um access token (curto, 15 min) e um refresh token (longo, 7 dias).
  5. O cliente envia Authorization: Bearer <access_token> nas rotas protegidas.
  6. Quando o access token expira, o cliente troca o refresh token por um par novo em POST /refresh.
  7. No logout, os tokens daquela sessão são revogados.

Configurando

Gere um segredo forte. O comando grava o JWT_SECRET no seu .env:

php vendor/bin/haki key:generate

Pronto, nada mais é obrigatório. Para mudar os padrões, use $app->auth() no bootstrap:

bootstrap/app.php
$app->auth([
    'secret'     => getenv('JWT_SECRET'),
    'expires_in' => 900,      // access token: 15 minutos
    'refresh_in' => 604800,   // refresh token: 7 dias
    'issuer'     => 'minha-api',
]);

Atenção

O conteúdo de um JWT pode ser lido por qualquer pessoa (ele é só assinado, não criptografado). Nunca coloque senhas, documentos ou dados sensíveis nos claims.

O que o Haki garante

  • O algoritmo é sempre o configurado: tokens com "alg": "none" ou com outro algoritmo são recusados.
  • A assinatura é comparada em tempo constante, o que protege contra ataques de tempo.
  • Tokens expirados, adulterados, malformados ou sem os claims obrigatórios recebem 401.
  • Não existe segredo padrão: sem JWT_SECRET, a autenticação não inicia.
  • O cliente sempre recebe uma mensagem genérica. O motivo real aparece só na dica, em desenvolvimento.

Login e tokens

Quem faz o quê

No login, o trabalho é dividido em duas partes:

  • A sua aplicação confere se o e-mail e a senha estão certos. Só ela sabe onde os usuários estão guardados.
  • O Haki gera os tokens para o usuário que você já conferiu, com $auth->login($id).

Nesta página, vamos montar o login completo, em quatro arquivos.

Antes de começar

Gere o segredo dos tokens com php vendor/bin/haki key:generate. Veja Configurando.

0. Guardando a senha no cadastro

A senha nunca é salva como foi digitada. No cadastro, gere um hash com password_hash() e salve o hash:

$hash = password_hash($senhaDigitada, PASSWORD_DEFAULT);
// "$2y$10$Lq7..." ← é isso que vai para o banco

No login, password_verify($senhaDigitada, $hash) diz se a senha confere. Nem você consegue descobrir a senha original a partir do hash, e é exatamente essa a ideia.

1. A regra de login fica em um service

Conferir senha é regra de negócio, então fica em app/Services. O service usa um repository para encontrar o usuário:

app/Services/LoginService.php
<?php

declare(strict_types=1);

namespace App\Services;

use App\Contracts\UsuarioRepositoryInterface;
use App\Models\Usuario;
use Haki\Exceptions\HttpException;

final class LoginService
{
    public function __construct(private readonly UsuarioRepositoryInterface $usuarios)
    {
    }

    public function autenticar(string $email, string $senha): Usuario
    {
        $usuario = $this->usuarios->buscarPorEmail($email);

        // Mesma mensagem nos dois casos: não revela quais e-mails existem.
        if ($usuario === null || !password_verify($senha, $usuario->senhaHash)) {
            throw new HttpException(401, 'E-mail ou senha incorretos');
        }

        return $usuario;
    }
}
Por que a mesma mensagem?

Se a API respondesse "e-mail não encontrado" num caso e "senha errada" no outro, qualquer pessoa conseguiria descobrir quais e-mails têm conta. Com uma mensagem só, isso não é possível.

2. A validação dos dados

app/Requests/LoginRequest.php
<?php

declare(strict_types=1);

namespace App\Requests;

use Haki\Validation\FormRequest;
use Haki\Validation\Rule;

final class LoginRequest extends FormRequest
{
    public function rules(Rule $rule): array
    {
        return [
            'email' => $rule->email(),
            'senha' => $rule->text(),
        ];
    }
}

3. O controller só conecta as peças

app/Controllers/AuthController.php
<?php

declare(strict_types=1);

namespace App\Controllers;

use App\Requests\LoginRequest;
use App\Services\LoginService;
use Haki\Auth\Auth;

final class AuthController
{
    public function __construct(private readonly LoginService $login)
    {
    }

    public function login(LoginRequest $request, Auth $auth): array
    {
        $usuario = $this->login->autenticar($request->email, $request->senha);

        return $auth->login($usuario->id, ['role' => $usuario->perfil]);
    }
}

Lendo de cima para baixo: o LoginRequest já garantiu que o e-mail e a senha foram enviados; o service confere a senha; o $auth->login() gera os tokens.

4. A rota

routes/api.php

Dados extras no token

O segundo argumento de login() adiciona informações (claims) ao token. Use para dados pequenos que você consulta sempre, como o perfil:

$auth->login($usuario->id, ['role' => 'admin', 'nome' => $usuario->nome]);

Esses dados ficam disponíveis em $request->user() nas rotas protegidas. Os nomes sub, iat, exp, jti, fid e iss são reservados e não podem ser usados.

Atenção

Qualquer pessoa com o token consegue ler o que está dentro dele. Nunca coloque senha, CPF ou outros dados sensíveis nos claims.

Usando o token no cliente

Em toda requisição a uma rota protegida, o cliente envia o access token no cabeçalho Authorization, com a palavra Bearer e um espaço antes:

curl http://localhost:8000/eu -H "Authorization: Bearer eyJhbGciOi..."
JavaScript
const resposta = await fetch('http://localhost:8000/eu', {
  headers: { Authorization: `Bearer ${accessToken}` },
});

No próximo passo, veja como proteger as rotas para exigir esse token.

Protegendo rotas

Exigindo login: ->auth()

Por padrão, toda rota é pública: qualquer pessoa pode chamar. Para exigir que o cliente esteja logado, adicione ->auth():

$app->get('/perfil', [PerfilController::class, 'show'])->auth();

Com isso, antes de chamar o controller, o Haki:

  1. Lê o token do cabeçalho Authorization: Bearer ....
  2. Confere a assinatura, a validade e se o token não foi revogado (logout).
  3. Se tudo estiver certo, preenche $request->user() e chama o controller.
  4. Se algo falhar, responde 401 e o controller nem é chamado.

Exigindo um perfil: ->role()

Algumas rotas são só para certos usuários, como administradores. ->role() exige um perfil específico e já inclui o ->auth():

// Só administradores
$app->get('/admin/painel', [AdminController::class, 'painel'])->role('admin');

// Administradores OU gerentes
$app->get('/relatorios', [RelatorioController::class, 'index'])->role('admin', 'gerente');

O perfil vem do claim role que você colocou no login: $auth->login($id, ['role' => 'admin']). A comparação é exata: 'Admin' e 'admin' são perfis diferentes.

Protegendo várias rotas de uma vez

Em vez de repetir ->auth() em cada rota, agrupe:

routes/api.php
// Públicas
$app->post('/login', [AuthController::class, 'login']);
$app->post('/refresh', [AuthController::class, 'refresh']);

// Qualquer usuário logado
$app->group('/', function (Haki $app) {
    $app->get('/eu', [AuthController::class, 'eu']);
    $app->post('/logout', [AuthController::class, 'logout']);
    $app->get('/pedidos', [PedidoController::class, 'index']);
})->auth();

// Só administradores
$app->group('/admin', function (Haki $app) {
    $app->get('/usuarios', [AdminController::class, 'usuarios']);
    $app->delete('/usuarios/{id}', [AdminController::class, 'remover']);
})->role('admin');

Perfis em grupos aninhados

Cada ->role() é um requisito a mais. Uma rota com ->role('gerente') dentro de um grupo com ->role('admin') exige os dois perfis ao mesmo tempo, o que normalmente não é o que se quer. Para aceitar um ou outro, liste os dois na mesma chamada: ->role('admin', 'gerente').

401 ou 403?

São dois "não" diferentes:

StatusQuer dizerQuando acontece
401"Não sei quem você é."Sem token, token inválido, vencido ou revogado
403"Sei quem você é, mas você não pode."Token válido, mas sem o perfil exigido
 
{ "erro": "Token não informado", "status": 401 }

No front-end, a reação a cada um é diferente: com 401, tente renovar o token com o refresh token e, se não der, mande para a tela de login. Com 403, mostre que a pessoa não tem permissão; fazer login de novo não resolve.

Respostas 401 trazem o cabeçalho WWW-Authenticate: Bearer, o padrão do HTTP para dizer que tipo de credencial é esperado.

Usuário autenticado

Descobrindo quem fez a requisição

Em rotas com ->auth(), $request->user() devolve quem está logado. Você não precisa ler o token nem buscar nada: o Haki já validou e montou a identidade.

public function eu(Request $request): array
{
    return ['usuario' => $request->user()];
}
{ "usuario": { "id": "1", "role": "admin" } }

O que a identidade oferece

UsoRetorna
$user->idO ID do usuário, sempre como texto ('1')
$user->roleO perfil, ou null
$user->get('nome')Um dado extra que você colocou no login
$user->get('nome', 'Visitante')O mesmo, com valor padrão
$user->hasRole('admin', 'gerente')true se tiver um dos perfis
$user->claimsTodos os dados do token, inclusive os de controle

Exemplos de uso

// Buscar os pedidos só do usuário logado
public function index(Request $request): array
{
    $idUsuario = (int) $request->user()->id;   // o id vem como texto; converta se o banco usa número

    return ['pedidos' => $this->pedidos->doUsuario($idUsuario)];
}

// Impedir que alguém veja o pedido de outra pessoa
public function show(int $id, Request $request): array
{
    $pedido = $this->pedidos->buscar($id) ?? throw new HttpException(404, 'Pedido não encontrado');
    $usuario = $request->user();

    if ($pedido->usuarioId !== (int) $usuario->id && !$usuario->hasRole('admin')) {
        throw new HttpException(403, 'Este pedido não é seu');
    }

    return ['pedido' => $pedido];
}
Sempre confira o dono

->auth() garante que a pessoa está logada, mas não que o recurso é dela. Se a rota recebe um {id}, confira se ele pertence ao usuário (como no exemplo acima). Esquecer essa conferência é uma das falhas de segurança mais comuns em APIs.

Como a identidade vira JSON

Retornada em uma resposta, a identidade mostra id, role e os dados extras do login. Os dados de controle do token (iat, exp, jti, fid, iss) ficam de fora:

$auth->login(7, ['role' => 'membro', 'nome' => 'Usopp']);
// depois, em uma rota protegida:
return ['usuario' => $request->user()];
// { "usuario": { "id": "7", "role": "membro", "nome": "Usopp" } }

Validando um token manualmente

Em casos especiais, como uma rota pública que mostra algo a mais para quem está logado, valide o token você mesmo com $auth->authenticate(). Ele faz as mesmas verificações do ->auth() e lança AuthenticationException se o token for inválido:

use Haki\Auth\Auth;
use Haki\Exceptions\AuthenticationException;

$app->get('/vitrine', function (Request $request, Auth $auth) {
    $usuario = null;
    $token = $request->bearerToken();

    if ($token !== null) {
        try {
            $usuario = $auth->authenticate($token);   // devolve a identidade
        } catch (AuthenticationException) {
            // token inválido: segue como visitante
        }
    }

    return ['saudacao' => $usuario ? 'Olá de novo, ' . $usuario->get('nome') : 'Bem-vindo!'];
});

Quando user() é null

Em rotas sem ->auth(), user() é sempre null, mesmo que o cliente envie um token. A identidade só é preenchida depois que o token é validado. Assim, ninguém consegue se passar por outro usuário mandando dados forjados.

A identidade vem do token, não do banco

O Haki não consulta o seu banco de dados. A identidade traz o que estava no token no momento do login. Na prática:

  • Se o usuário mudar de nome ou de perfil, o token antigo continua com os dados antigos até vencer (no máximo 15 minutos, por padrão).
  • Se o usuário for bloqueado, o token antigo continua funcionando até vencer.

Para mudanças que precisam valer na hora, revogue os tokens dele com $auth->logoutAll($id) (veja Sair de todos os dispositivos). Se você precisa conferir o banco a cada requisição, crie um middleware próprio e aplique depois do ->auth():

app/Middleware/UsuarioAtivo.php
final class UsuarioAtivo implements MiddlewareInterface
{
    public function __construct(private readonly UsuarioRepositoryInterface $usuarios)
    {
    }

    public function handle(Request $request, callable $next): Response
    {
        $usuario = $this->usuarios->buscarPorId((int) $request->user()?->id);

        if ($usuario === null || $usuario->bloqueado) {
            throw new HttpException(403, 'Conta bloqueada');
        }

        return $next($request);
    }
}
$app->group('/', function (Haki $app) {
    // ...
})->auth()->middleware(UsuarioAtivo::class);

O custo é uma consulta ao banco por requisição. Use só se a sua aplicação realmente precisar.

Refresh e logout

Por que dois tokens?

No login, o cliente recebe dois tokens com papéis diferentes:

Access tokenRefresh token
Para que serveAcessar as rotas protegidasPedir um access token novo
Validade padrão15 minutos7 dias
Enviado emToda requisição protegidaSó em POST /refresh
Se for roubadoServe por poucos minutosÉ detectado na primeira vez que for reutilizado

A vantagem: o token que viaja em toda requisição (e por isso tem mais chance de vazar) vence rápido, e o usuário não precisa digitar a senha a cada 15 minutos.

Renovando os tokens

Crie a rota de refresh. Ela é pública, porque é usada justamente quando o access token já venceu:

app/Controllers/AuthController.php
public function refresh(Request $request, Auth $auth): array
{
    return $auth->refresh($request->input('refresh_token'));
}
routes/api.php
$app->post('/refresh', [AuthController::class, 'refresh']);
curl -X POST http://localhost:8000/refresh \
     -H "Content-Type: application/json" \
     -d '{"refresh_token": "9f2c4e1a7b..."}'

A resposta tem o mesmo formato do login: um access_token novo e um refresh_token novo.

O fluxo no cliente

  1. Faz a requisição normalmente com o access token.
  2. Se receber 401, chama POST /refresh com o refresh token guardado.
  3. Se o refresh der certo, guarda os dois tokens novos e repete a requisição original.
  4. Se o refresh também der 401, a sessão acabou: manda o usuário para a tela de login.
JavaScript
async function api(url, opcoes = {}) {
  let resposta = await fetch(url, comToken(opcoes));

  if (resposta.status === 401 && await renovarTokens()) {
    resposta = await fetch(url, comToken(opcoes));   // tenta de novo com o token novo
  }

  return resposta;
}

async function renovarTokens() {
  const r = await fetch('/refresh', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ refresh_token: tokens.refresh }),
  });

  if (!r.ok) { irParaLogin(); return false; }

  const novos = await r.json();
  tokens.access = novos.access_token;
  tokens.refresh = novos.refresh_token;   // guarde o novo: o antigo não vale mais
  return true;
}

Rotação: cada refresh token vale uma vez

Ao usar um refresh token, o cliente recebe um par novo e o refresh token usado deixa de valer. Por isso o cliente deve sempre substituir o refresh token guardado pelo novo.

Detecção de roubo

Imagine que alguém copiou o refresh token da Nami:

  1. O atacante usa o token copiado e recebe um par novo.
  2. Mais tarde, o app da Nami usa o mesmo token (que já foi usado pelo atacante).
  3. O Haki percebe que um refresh token já usado apareceu de novo: há duas cópias, e uma é ilegítima.
  4. Para proteger a conta, ele revoga todas as sessões da Nami, inclusive a do atacante.
  5. A Nami faz login de novo; o atacante perde o acesso.

Você não precisa programar nada disso: acontece sozinho dentro do $auth->refresh().

Quando o refresh falha

Em todos estes casos, a resposta é 401 "Refresh token inválido ou expirado": token não enviado, inexistente, vencido, revogado por logout, ou reutilizado.

Logout

logout() encerra a sessão atual: o access token usado na requisição e os refresh tokens daquele login deixam de valer. As sessões em outros dispositivos continuam.

app/Controllers/AuthController.php
public function logout(Request $request, Auth $auth): null
{
    $auth->logout($request);

    return null; // 204 sem conteúdo
}
routes/api.php
$app->post('/logout', [AuthController::class, 'logout'])->auth();   // precisa de ->auth()

A rota precisa de ->auth() porque o logout usa o token da requisição para saber qual sessão encerrar. No cliente, depois do logout, apague os tokens guardados.

Sair de todos os dispositivos

logoutAll() revoga todos os tokens já emitidos para o usuário, em todos os dispositivos:

$auth->logoutAll($usuario->id);

Use quando:

  • A pessoa trocar a senha (outras sessões abertas podem ser de quem descobriu a senha antiga).
  • O perfil mudar, para o novo valer imediatamente.
  • A conta for bloqueada.
  • O usuário clicar em "sair de todos os dispositivos".
// Exemplo: trocar a senha
public function trocarSenha(TrocarSenhaRequest $request, Auth $auth): array
{
    $id = (int) $request->user()->id;

    $this->usuarios->atualizarSenha($id, password_hash($request->nova_senha, PASSWORD_DEFAULT));
    $auth->logoutAll($id);

    return $auth->login($id);   // devolve tokens novos para o dispositivo atual
}
Nota

logoutAll() revoga os tokens emitidos antes da chamada. Um login() feito logo em seguida, como no exemplo acima, gera tokens novos que funcionam normalmente.

Chaves RS256

HS256 ou RS256?

O token JWT é assinado: uma espécie de lacre que prova que foi a sua API que o emitiu e que ninguém o alterou. Há duas formas de fazer esse lacre:

HS256 (padrão)RS256
Como funcionaUm único segredo assina e confereUm par de chaves: a privada assina, a pública confere
Quem pode conferir os tokensSó quem tem o segredo (que também pode criar tokens)Qualquer um com a chave pública (que não consegue criar tokens)
ConfiguraçãoUma linha no .envDois arquivos de chave
Use quandoSó a sua API lida com os tokensOutros serviços precisam conferir os tokens da sua API

Uma analogia: no HS256, todos que conferem a assinatura têm a mesma chave do cofre, e por isso também poderiam abri-lo. No RS256, a chave privada fica só com quem emite; os outros recebem uma chave que só serve para conferir.

Na dúvida, fique com o HS256. Ele é mais simples e igualmente seguro para uma API só.

1. Gerando as chaves

php vendor/bin/haki key:generate --rsa
✔ Chaves RSA geradas em C:\projetos\minha-api\storage\keys
  Adicione ao .env:
    JWT_ALGORITHM=RS256
    JWT_PRIVATE_KEY=storage/keys/private.pem
    JWT_PUBLIC_KEY=storage/keys/public.pem

O comando cria duas chaves RSA de 2048 bits em storage/keys/. Se elas já existirem, use --force para gerar novas (isso desconecta todos os usuários).

Se preferir gerar com o OpenSSL diretamente:

openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out storage/keys/private.pem
openssl rsa -in storage/keys/private.pem -pubout -out storage/keys/public.pem

2. Configurando o .env

.env
JWT_ALGORITHM=RS256
JWT_PRIVATE_KEY=storage/keys/private.pem
JWT_PUBLIC_KEY=storage/keys/public.pem

Pronto. O resto (login, refresh, ->auth()) funciona igual ao HS256, sem mudar nenhum código. O JWT_SECRET não é usado no RS256.

Configurando pelo código

Em vez do .env, você pode configurar no bootstrap:

$app->auth([
    'algorithm'   => 'RS256',
    'private_key' => 'storage/keys/private.pem', // caminho relativo à raiz, absoluto, ou o conteúdo PEM
    'public_key'  => 'storage/keys/public.pem',
]);

Se você informar só a chave privada, a pública é calculada a partir dela.

Um serviço que só confere tokens

Em outro serviço que só precisa saber se o token é válido, configure apenas a chave pública:

$app->auth(['algorithm' => 'RS256', 'public_key' => 'chaves/public.pem']);

Esse serviço consegue proteger rotas com ->auth() e ler $request->user(), mas não consegue emitir tokens: se tentar chamar $auth->login(), recebe um erro explicando que falta a chave privada.

O que o Haki confere nas chaves

  • As chaves precisam ser RSA válidas, com pelo menos 2048 bits. Chaves menores são recusadas na hora.
  • Um token assinado com HS256 é recusado por uma API configurada com RS256 (e vice-versa). Isso impede um ataque conhecido em que o atacante tenta assinar um token usando a chave pública como se fosse segredo.
Proteja a chave privada

Ela é tão sensível quanto uma senha: quem tiver a chave privada consegue criar tokens de qualquer usuário. Nunca envie para o Git (o .gitignore do init já deixa storage/keys/ de fora) e nunca compartilhe com outros serviços: eles só precisam da pública.

Armazenamento de tokens

Por que guardar alguma coisa?

Um JWT é autossuficiente: o servidor confere a assinatura e pronto, sem consultar nada. O problema é que, sozinho, ele não pode ser cancelado antes de vencer. Para o logout e o refresh token funcionarem, o Haki precisa lembrar de algumas coisas:

  • Quais refresh tokens existem, se já foram usados e a qual login pertencem. Só o hash é guardado, nunca o token em si.
  • Quais access tokens foram revogados por logout, até a data em que venceriam.
  • A data do último logoutAll() de cada usuário.

SQLite automático

Por padrão, essas informações ficam em um arquivo SQLite que é criado sozinho na primeira requisição que usa autenticação:

storage/ └── haki.sqlite criado automaticamente

Você não precisa criar tabela nem rodar migração. Só precisa de duas coisas:

  • A extensão pdo_sqlite ativa no PHP. Se não estiver, a mensagem de erro explica como ativar.
  • Permissão de escrita na pasta storage/ para o usuário do PHP.

Se preferir criar o banco de forma explícita (no deploy, por exemplo, para descobrir problemas de permissão antes do primeiro acesso):

php vendor/bin/haki auth:install

Limpeza dos registros vencidos

Tokens vencidos não servem para nada e são apagados sozinhos, de tempos em tempos, durante as requisições. Em APIs com muito tráfego, vale agendar a limpeza:

php vendor/bin/haki auth:clean
crontab (todo dia às 3h)
0 3 * * * cd /var/www/minha-api && php vendor/bin/haki auth:clean

Mudando o local do arquivo

$app->auth([
    'secret'   => getenv('JWT_SECRET'),
    'database' => 'storage/tokens/auth.sqlite',   // relativo à raiz do projeto
]);

Ou pelo .env: JWT_DATABASE=storage/tokens/auth.sqlite.

Um servidor ou vários?

O SQLite atende muito bem uma API rodando em um servidor, mesmo com bastante tráfego. O problema aparece com vários servidores atrás de um balanceador: cada um teria o próprio arquivo, e um logout feito no servidor A não seria conhecido pelo servidor B. Nesse caso, guarde os tokens em um lugar compartilhado, como MySQL ou Redis.

Usando outro banco

Implemente a interface TokenStore e informe a classe em $app->auth(). Este é um exemplo completo com MySQL:

tabelas (MySQL)
CREATE TABLE haki_refresh_tokens (
    token_hash CHAR(64) PRIMARY KEY,
    user_id    VARCHAR(64) NOT NULL,
    family_id  CHAR(32) NOT NULL,
    claims     JSON NOT NULL,
    created_at INT NOT NULL,
    expires_at INT NOT NULL,

    revoked_at INT NULL,

);

    jti        CHAR(32) PRIMARY KEY,

);

    user_id        VARCHAR(64) PRIMARY KEY,
    revoked_before INT NOT NULL
);
app/Repositories/MysqlTokenStore.php
<?php

declare(strict_types=1);

namespace App\Repositories;

use Haki\Auth\Storage\RefreshTokenRecord;
use Haki\Auth\Storage\TokenStore;
use PDO;

final class MysqlTokenStore implements TokenStore
{
    public function __construct(private readonly PDO $pdo)
    {
    }

    public function revokeAccessToken(string $jti, int $expiresAt): void
    {
        $this->pdo->prepare('REPLACE INTO haki_revoked_tokens (jti, expires_at) VALUES (?, ?)')
            ->execute([$jti, $expiresAt]);
    }

    public function isAccessTokenRevoked(string $jti): bool
    {
        $stmt = $this->pdo->prepare('SELECT 1 FROM haki_revoked_tokens WHERE jti = ?');
        $stmt->execute([$jti]);

        return $stmt->fetchColumn() !== false;
    }

    public function revokeUser(string $userId, int $before): void
    {
        $this->pdo->prepare(
            'INSERT INTO haki_user_revocations (user_id, revoked_before) VALUES (?, ?)
             ON DUPLICATE KEY UPDATE revoked_before = GREATEST(revoked_before, VALUES(revoked_before))'
        )->execute([$userId, $before]);
    }

    public function userRevokedBefore(string $userId): ?int
    {
        $stmt = $this->pdo->prepare('SELECT revoked_before FROM haki_user_revocations WHERE user_id = ?');
        $stmt->execute([$userId]);
        $value = $stmt->fetchColumn();

        return $value === false ? null : (int) $value;
    }

    public function saveRefreshToken(RefreshTokenRecord $r): void
    {
        $this->pdo->prepare(
            'INSERT INTO haki_refresh_tokens (token_hash, user_id, family_id, claims, created_at, expires_at)
             VALUES (?, ?, ?, ?, ?, ?)'
        )->execute([$r->hash, $r->userId, $r->familyId, json_encode($r->claims), $r->createdAt, $r->expiresAt]);
    }

    public function findRefreshToken(string $hash): ?RefreshTokenRecord
    {
        $stmt = $this->pdo->prepare('SELECT * FROM haki_refresh_tokens WHERE token_hash = ?');
        $stmt->execute([$hash]);
        $row = $stmt->fetch(PDO::FETCH_ASSOC);

        if ($row === false) {
            return null;
        }

        return new RefreshTokenRecord(
            $row['token_hash'],
            $row['user_id'],
            $row['family_id'],
            json_decode($row['claims'], true) ?: [],
            (int) $row['created_at'],
            (int) $row['expires_at'],
            $row['used_at'] !== null ? (int) $row['used_at'] : null,
            $row['revoked_at'] !== null ? (int) $row['revoked_at'] : null,
        );
    }

    public function consumeRefreshToken(string $hash, int $now): bool
    {
        // Atômico: só uma requisição consegue marcar o token como usado.
        $stmt = $this->pdo->prepare(
            'UPDATE haki_refresh_tokens SET used_at = ?
             WHERE token_hash = ? AND used_at IS NULL AND revoked_at IS NULL'
        );
        $stmt->execute([$now, $hash]);

        return $stmt->rowCount() === 1;
    }

    public function revokeFamily(string $familyId, int $now): void
    {
        $this->pdo->prepare('UPDATE haki_refresh_tokens SET revoked_at = ? WHERE family_id = ? AND revoked_at IS NULL')
            ->execute([$now, $familyId]);
    }

    public function purgeExpired(int $now): int
    {
        $a = $this->pdo->prepare('DELETE FROM haki_revoked_tokens WHERE expires_at <= ?');
        $a->execute([$now]);
        $b = $this->pdo->prepare('DELETE FROM haki_refresh_tokens WHERE expires_at <= ?');
        $b->execute([$now]);

        return $a->rowCount() + $b->rowCount();
    }
}
bootstrap/app.php
$app->auth([
    'secret'  => getenv('JWT_SECRET'),
    'storage' => new MysqlTokenStore($pdo),
]);
O ponto mais importante

consumeRefreshToken() precisa ser atômico: se duas requisições usarem o mesmo refresh token ao mesmo tempo, só uma pode ter sucesso. No SQL, isso se resolve com UPDATE ... WHERE used_at IS NULL e conferindo se uma linha foi afetada, como no exemplo. No Redis, use SET ... NX ou um script Lua.

Tipagem

Por que tipar

Tipar é dizer, no próprio código, que tipo de valor cada parte espera e devolve: function buscar(int $id): ?Produto diz "recebo um número inteiro e devolvo um Produto ou nada". O PHP passa a conferir isso a cada chamada.

Sem tipo, o PHP aceita qualquer coisa e tenta converter sozinho. O erro aparece longe de onde nasceu, ou nem aparece:

// Sem tipos: "abc" vira 0, e o código segue como se estivesse tudo certo
function desconto($preco, $percentual) { return $preco - $preco * $percentual / 100; }

desconto("abc", 10);   // 0, sem nenhum aviso

// Com tipos: o erro aparece na hora, apontando a linha
function desconto(float $preco, int $percentual): float { ... }

desconto("abc", 10);   // TypeError: Argument #1 ($preco) must be of type float, string given

Com tipos, o editor também completa métodos, avisa erros enquanto você digita e qualquer pessoa entende a função sem precisar ler o corpo dela.

Tipagem obrigatória: $app->requireTypes()

O Haki pode exigir tipos no código do projeto. Com isto no bootstrap/app.php (o haki init já cria assim):

bootstrap/app.php
$app->requireTypes();

toda classe do projeto que o Haki for usar (controllers, services, repositories, classes de validação, middlewares) é conferida antes de rodar. Se faltar algum tipo, a requisição responde com erro dizendo exatamente o que corrigir.

Container de dependências

O problema que ele resolve

Imagine um controller que precisa de um service, que precisa de um repository, que precisa de uma conexão com o banco. Sem ajuda, você criaria tudo à mão, em ordem:

// Sem container: você monta a cadeia inteira, em todo lugar
$pdo = new PDO('mysql:host=localhost;dbname=loja', 'root', 'senha');
$repositorio = new PdoPedidoRepository($pdo);
$frete = new CalculadoraDeFrete();
$service = new CriarPedidoService($repositorio, $frete);
$controller = new PedidoController($service);

O container faz isso por você. Ele lê o construtor de cada classe, descobre do que ela precisa e cria tudo em cadeia. Esse processo se chama injeção de dependências: em vez de a classe criar o que usa, ela recebe pronto.

Criação automática

Para classes comuns (não interfaces), você não configura nada:

final class PedidoController
{
    public function __construct(private readonly CriarPedidoService $criarPedido) {}
}

final class CriarPedidoService
{
    public function __construct(private readonly CalculadoraDeFrete $frete) {}
}

// Ao chamar a rota, o Haki cria: CalculadoraDeFrete → CriarPedidoService → PedidoController

Funciona com qualquer profundidade e também nos middlewares, nas classes de validação e nos parâmetros dos métodos dos controllers.

Interfaces precisam de um bind

Quando uma classe pede uma interface, o container não tem como adivinhar qual implementação usar: pode haver várias (MySQL, arquivo, API externa). Você diz qual, uma vez, no bootstrap:

bootstrap/app.php
use App\Contracts\UsuarioRepositoryInterface;
use App\Repositories\PdoUsuarioRepository;

$app->container()->bind(UsuarioRepositoryInterface::class, PdoUsuarioRepository::class);

Lendo: "quando alguém pedir UsuarioRepositoryInterface, entregue um PdoUsuarioRepository". Se as suas classes seguem um padrão de nomes, dá para dispensar esse bind com a descoberta automática. Todas as classes que pedem a interface passam a receber essa implementação. Para trocar, você muda só essa linha.

Se você esquecer o bind, o erro explica o que fazer:

Não foi possível criar App\Contracts\UsuarioRepositoryInterface: a classe é uma interface.
Dica: Registre uma implementação: $app->container()->bind(UsuarioRepositoryInterface::class, SuaClasse::class);

Descoberta automática: sem bind para cada interface

Escrever um bind() para cada interface cansa. Se as suas classes seguem um padrão de nomes, o Haki encontra a implementação sozinho. O haki init já deixa isto no bootstrap/app.php:

bootstrap/app.php
$app->container()->discover('App\\Contracts', 'App\\Repositories');

A partir daí, quando alguém pedir uma interface de App\Contracts, o Haki tira o Interface do fim do nome e procura a classe em App\Repositories:

App\Contracts\ProdutoRepositoryInterface
    → procura App\Repositories\ProdutoRepository
    → procura App\Repositories\PdoProdutoRepository

Você cria a interface e a classe seguindo os nomes, e não escreve nenhum bind. Subpastas também funcionam: App\Contracts\Fiscal\NotaRepositoryInterface procura em App\Repositories\Fiscal\.

Outros padrões de nome

Se o seu projeto usa outro padrão, informe na chamada:

$app->container()->discover(
    from: 'App\\Domain\\Contracts',       // onde ficam as interfaces
    to: 'App\\Infra\\Persistence',        // onde ficam as classes
    suffix: 'Contract',                   // parte removida do fim do nome da interface
    prefix: '',                           // parte removida do começo (ex.: 'I')
    patterns: ['Mysql{name}', '{name}'],  // nomes procurados; {name} = nome sem prefixo/sufixo
);

$app->container()->discover('App\\Contracts', 'App\\Repositories');

Regras de segurança

  • O bind manual sempre vence. Para um caso fora do padrão, basta um bind(); o resto continua automático.
  • Nunca chuta. Se duas classes servirem (por exemplo, ProdutoRepository e PdoProdutoRepository), é erro, e a mensagem pede um bind para escolher.
  • A classe encontrada precisa implementar a interface. Uma classe com o nome certo, mas sem o implements, é recusada.
  • É opcional. Sem discover(), tudo funciona só com bind(), como antes.

bind, singleton e instance

O segundo argumento é opcional quando é a própria classe: singleton(CalculadoraDeFrete::class) faz o container reaproveitar sempre o mesmo objeto dessa classe.

Criando com uma função

Quando o construtor precisa de valores (texto, número, configuração do .env), o container não tem como adivinhá-los. Ensine como criar com uma função:

bootstrap/app.php
use Haki\Support\Env;

$app->container()->singleton(PDO::class, function () {
    return new PDO(
        'mysql:host=' . Env::get('DB_HOST') . ';dbname=' . Env::get('DB_NAME'),
        Env::get('DB_USER'),
        Env::get('DB_PASS'),
        [PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION],
    );
});

A partir daí, qualquer repository que peça PDO $pdo no construtor recebe essa mesma conexão. A função também recebe o container, para pegar outras dependências:

use Haki\Container\Container;

$app->container()->bind(ServicoDeEmail::class, function (Container $c) {
    return new ServicoDeEmail($c->get(ClienteSmtp::class), Env::get('EMAIL_REMETENTE'));
});

Parâmetros com valor padrão

Se um parâmetro do construtor não é uma classe mas tem valor padrão, o container usa o padrão. Isso é útil para configurações opcionais:

final class Cors implements MiddlewareInterface
{
    public function __construct(private readonly string $origem = 'http://localhost:5173') {}
}

Pegando objetos do container

Normalmente o container trabalha sozinho, mas você pode pedir objetos a ele diretamente:

$container = $app->container();

$service = $container->get(CriarPedidoService::class);    // cria (ou reaproveita, se singleton)
$container->has(UsuarioRepositoryInterface::class);       // true se registrado ou se a classe existe
$novo = $container->build(CalculadoraDeFrete::class);     // sempre cria um novo, ignorando registros

O Haki já registra, por conta própria: a aplicação (Haki), o Container, o Router, o Auth, o AuthConfig e o TokenStore. Qualquer classe pode recebê-los pelo construtor.

SOLID na prática

Por que se importar

SOLID são cinco princípios que deixam o código fácil de mudar sem quebrar o que já funciona. A estrutura de pastas recomendada já empurra você na direção certa. Veja como cada princípio aparece em um projeto Haki.

S: responsabilidade única

Cada classe tem um único motivo para mudar.

O controller lida com HTTP, o service com a regra de negócio e o repository com os dados. Se a regra de desconto mudar, você só mexe no service.

// Ruim: o controller faz tudo
public function store(Request $request): array
{
    $pdo = new PDO('mysql:...');
    $total = $request->input('valor') * 0.9; // regra de desconto escondida aqui
    $pdo->prepare('INSERT INTO pedidos ...')->execute([...]);
    return ['ok' => true];
}

// Bom: cada um no seu lugar
public function store(Request $request, Response $response): Response
{
    $pedido = $this->criarPedido->executar($request->only(['produto_id', 'quantidade']));

    return $response->json(['pedido' => $pedido], 201);
}

O: aberto para extensão

Adicione comportamento criando classes novas, sem editar as que já funcionam.

No Haki, isso aparece nos middlewares: para adicionar log, CORS ou limite de acesso, você cria um middleware novo e registra. Nenhum controller muda.

L: substituição

Qualquer implementação de uma interface deve funcionar no lugar da outra.

Um ArrayUsuarioRepository (para testes) e um PdoUsuarioRepository (produção) seguem o mesmo contrato. O service não percebe a troca.

I: interfaces enxutas

Prefira interfaces pequenas e específicas.

interface UsuarioRepositoryInterface
{
    public function buscarPorId(int $id): ?Usuario;
    public function buscarPorEmail(string $email): ?Usuario;
}

Se só o painel de relatórios precisa de estatísticas, crie uma RelatorioRepositoryInterface separada em vez de inchar essa.

D: dependa de abstrações

Classes de alto nível dependem de interfaces, não de implementações concretas.

O service pede UsuarioRepositoryInterface, e o bootstrap decide qual classe entregar. Para trocar de MySQL para uma API externa, você muda uma linha:

bootstrap/app.php
$app->container()->bind(UsuarioRepositoryInterface::class, PdoUsuarioRepository::class);
// amanhã:
$app->container()->bind(UsuarioRepositoryInterface::class, ApiUsuarioRepository::class);

Receita para um recurso novo

Para adicionar, por exemplo, produtos à API:

  1. Model

    app/Models/Produto.php: os dados e o jsonSerialize().

  2. Contrato

    app/Contracts/ProdutoRepositoryInterface.php: os métodos de acesso a dados.

  3. Repository

    app/Repositories/PdoProdutoRepository.php: implementa a interface com SQL.

  4. Service (se houver regra)

    app/Services/CriarProdutoService.php: valida e aplica a regra de negócio.

  5. Controller

    app/Controllers/ProdutoController.php: lê a requisição, chama o service e retorna.

  6. Bind e rotas

    Um bind() no bootstrap e as rotas em routes/api.php.

Testes

Por que testar

Um teste automatizado é um código que chama a sua API e confere se a resposta está certa. Depois de escrito, ele roda em segundos, quantas vezes você quiser. Assim, quando você muda uma parte do código, descobre na hora se quebrou outra.

No Haki, dá para testar a API inteira sem subir servidor: $app->handle() processa uma requisição e devolve a resposta, como se ela tivesse vindo da internet.

Configurando o PHPUnit

  1. Instale o PHPUnit 
    composer require --dev phpunit/phpunit

    O --dev indica que ele só é usado em desenvolvimento e não vai para a produção.

  2. Ensine o Composer a carregar a pasta tests/
    composer.json
    "autoload-dev": {
    "psr-4": {
        "Tests\\": "tests/"
    }
}

    Depois, rode composer dump-autoload.

  3. Crie o arquivo de configuração
    phpunit.xml
    <?xml version="1.0" encoding="UTF-8"?>
<phpunit bootstrap="vendor/autoload.php" colors="true">
    <testsuites>
        <testsuite name="API">
            <directory>tests</directory>
        </testsuite>
    </testsuites>
</phpunit>
  4. Rode os testes 
    php vendor/bin/phpunit

tests/HomeTest.php
<?php

declare(strict_types=1);

namespace Tests;

use Haki\Http\Request;
use PHPUnit\Framework\TestCase;

final class HomeTest extends TestCase
{
    public function testHomeResponde(): void

  1. Envie o código e instale as dependências 
    composer install --no-dev --optimize-autoloader

    --no-dev deixa de fora o que só serve em desenvolvimento (como o PHPUnit), e --optimize-autoloader deixa o carregamento das classes mais rápido.

  2. Crie o .env da produção 
    cp .env.example .env

    Depois, preencha o resto (banco, APP_ENV=production...).

  3. Prepare o banco de tokens 
    php vendor/bin/haki auth:install
  4. Configure o servidor web

    Aponte para public/ e redirecione tudo para o index.php. Veja os exemplos de Nginx e Apache.

  5. Agende a limpeza com auth:clean em um cron (veja auth:clean).

Desempenho

  • Ative o OPcache no php.ini (opcache.enable=1). Ele guarda o código PHP já compilado e é o ganho de velocidade mais simples que existe.
  • Use --optimize-autoloader no composer install.
  • Rotas públicas não tocam no banco de tokens. Rotas protegidas fazem uma consulta rápida a ele por requisição.

Trocando o segredo

Trocar o JWT_SECRET (ou as chaves RSA) invalida todos os tokens existentes, e todos os usuários precisam fazer login de novo. Faça isso se suspeitar de vazamento:

php vendor/bin/haki key:generate --force

Proteja o login contra força bruta

O Haki não limita tentativas de login. Sem limite, alguém pode testar milhares de senhas por minuto. Algumas formas de resolver:

  • Configurar limite de requisições no servidor web ou proxy (Nginx limit_req, Cloudflare).
  • Criar um middleware que conte as tentativas por IP ($request->ip()) e responda 429 ao passar do limite, guardando a contagem em Redis ou no banco.
  • Bloquear temporariamente a conta depois de várias senhas erradas seguidas.

Logs

Em produção, erros 500 são registrados no log do PHP (error_log) com a exceção, o arquivo e a linha, enquanto o cliente vê só "Erro interno do servidor". Confira onde o seu servidor guarda esse log (a diretiva error_log do php.ini) e acompanhe-o depois de cada deploy.

app/Database/Connection.php
<?php

declare(strict_types=1);

namespace App\Database;

use Haki\Support\Env;
use PDO;
use RuntimeException;

/**
 * Conexão com o banco, configurada pelas variáveis DB_* do .env.
 * A conexão só é aberta na primeira vez que pdo() é chamado.
 */
final class Connection
{
    private ?PDO $pdo = null;

    public function __construct(
        private readonly string $driver,
        private readonly string $database,
        private readonly string $host = '127.0.0.1',
        private readonly int $port = 3306,
        private readonly ?string $username = null,
        #[\SensitiveParameter] private readonly ?string $password = null,
    ) {
    }

    public static function fromEnv(string $basePath): self
    {
        $driver = (string) Env::get('DB_CONNECTION', 'sqlite');
        $database = (string) Env::get('DB_DATABASE', 'database/app.sqlite');

        if ($driver === 'sqlite' && !preg_match('#^([A-Za-z]:[\\\\/]|/)#', $database)) {
            $database = rtrim($basePath, '/\\') . DIRECTORY_SEPARATOR . $database;
        }

        return new self(
            $driver,
            $database,
            (string) Env::get('DB_HOST', '127.0.0.1'),
            (int) Env::get('DB_PORT', 3306),
            Env::get('DB_USERNAME'),
            Env::get('DB_PASSWORD'),
        );
    }

    public function pdo(): PDO
    {
        return $this->pdo ??= $this->connect();
    }

    private function connect(): PDO
    {
        $options = [
            PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION,
            PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,
        ];

        return match ($this->driver) {
            'sqlite' => new PDO('sqlite:' . $this->database, null, null, $options),
            'mysql' => new PDO(
                "mysql:host={$this->host};port={$this->port};dbname={$this->database};charset=utf8mb4",
                $this->username,
                $this->password,
                $options,
            ),
            default => throw new RuntimeException("DB_CONNECTION \"{$this->driver}\" não suportado. Use sqlite ou mysql."),
        };
    }
}

app/Repositories/PdoProdutoRepository.php
<?php

declare(strict_types=1);

namespace App\Repositories;

use App\Contracts\ProdutoRepositoryInterface;
use App\Database\Connection;
use App\Models\Produto;
use PDO;

final class PdoProdutoRepository implements ProdutoRepositoryInterface
{
    private readonly PDO $pdo;

    public function __construct(Connection $connection)
    {
        $this->pdo = $connection->pdo();
    }

    public function listar(int $pagina, int $porPagina): array
    {
        $stmt = $this->pdo->prepare('SELECT * FROM produtos ORDER BY id LIMIT :limite OFFSET :inicio');
        $stmt->bindValue(':limite', $porPagina, PDO::PARAM_INT);
        $stmt->bindValue(':inicio', ($pagina - 1) * $porPagina, PDO::PARAM_INT);
        $stmt->execute();

        $produtos = [];

        foreach ($stmt->fetchAll() as $linha) {
            $produtos[] = new Produto((int) $linha['id'], $linha['nome'], (float) $linha['preco'], (int) $linha['estoque']);
        }

        return $produtos;
    }

    public function buscar(int $id): ?Produto
    {
        $stmt = $this->pdo->prepare('SELECT * FROM produtos WHERE id = ?');
        $stmt->execute([$id]);
        $linha = $stmt->fetch();

        if (!$linha) {
            return null;
        }

        return new Produto((int) $linha['id'], $linha['nome'], (float) $linha['preco'], (int) $linha['estoque']);
    }

    public function criar(string $nome, float $preco, int $estoque): Produto
    {
        $stmt = $this->pdo->prepare('INSERT INTO produtos (nome, preco, estoque) VALUES (?, ?, ?)');
        $stmt->execute([$nome, $preco, $estoque]);

        return new Produto((int) $this->pdo->lastInsertId(), $nome, $preco, $estoque);
    }

    public function atualizar(int $id, string $nome, float $preco, int $estoque): void
    {
        $stmt = $this->pdo->prepare('UPDATE produtos SET nome = ?, preco = ?, estoque = ? WHERE id = ?');
        $stmt->execute([$nome, $preco, $estoque, $id]);
    }

    public function apagar(int $id): bool
    {
        $stmt = $this->pdo->prepare('DELETE FROM produtos WHERE id = ?');
        $stmt->execute([$id]);

        return $stmt->rowCount() > 0;
    }
}

    {

Problemas comuns

Os erros que mais aparecem, organizados pelo que você vê na tela. Use a busca (Ctrl + K) com um trecho da mensagem para chegar direto.

Antes de tudo

Deixe APP_ENV=development no .env enquanto desenvolve: assim cada erro vem com uma dica explicando a causa. E rode php vendor/bin/haki check e php vendor/bin/haki db: eles encontram boa parte dos problemas abaixo sozinhos.

Instalação

"The zip extension and unzip/7z commands are both missing"

Causa: o Composer baixa os pacotes compactados e o PHP está sem a extensão zip. A pasta vendor/ não é criada.

Solução: no php.ini (veja onde está com php --ini), troque ;extension=zip por extension=zip, abra o terminal de novo e rode composer require shankscode/haki outra vez.

"php não é reconhecido como um comando"

Causa: a pasta do PHP não está no PATH do Windows.

Solução: adicione a pasta (por exemplo, C:\php) às variáveis de ambiente do sistema, em Configurações → Sistema → Sobre → Configurações avançadas → Variáveis de Ambiente, e abra o terminal de novo.

"Your requirements could not be resolved" / "php ^8.2"

Causa: a versão do PHP é anterior à 8.2.

Solução: confira com php -v e atualize o PHP.

Classes e autoload

"Class ... not found" / "a classe não existe"

Causas mais comuns, nesta ordem:

  1. O namespace do arquivo não bate com a pasta. Em app/Controllers/ProdutoController.php, precisa ser namespace App\Controllers;.
  2. O nome da classe não é igual ao nome do arquivo (atenção às maiúsculas: ProdutoController ≠ produtoController).
  3. Faltou o use App\...; no arquivo que usa a classe.
  4. O composer.json não tem o autoload de App\, ou ele foi editado sem rodar composer dump-autoload.

Em desenvolvimento, a mensagem do Haki costuma trazer "Você quis dizer ...?" com o nome mais parecido que existe.

"... a classe é uma interface" / "Nenhuma implementação encontrada"

Causa: o controller pede uma interface e o Haki não sabe qual classe entregar.

Solução: confira se o bootstrap/app.php tem o discover('App\\Contracts', 'App\\Repositories') e se os nomes seguem o padrão (ProdutoRepositoryInterface → ProdutoRepository ou PdoProdutoRepository). Para nomes fora do padrão, use bind(). Veja Descoberta automática.

"Tipagem obrigatória: ... tem N problemas"

Causa: o bootstrap/app.php tem $app->requireTypes() e uma classe do projeto tem parâmetro, retorno ou propriedade sem tipo, ou não tem declare(strict_types=1).

Solução: a mensagem diz a classe, o método e a linha. Adicione os tipos e confira tudo com php vendor/bin/haki check. Veja Tipagem.

"Não sei como injetar $x em ..."

Causa: um parâmetro do método (ou do construtor) não é uma classe e não é um parâmetro da rota.

Solução: se é um valor da URL, o nome precisa ser igual ao da rota ({id} → $id). Se é configuração, dê um valor padrão ou crie a classe com uma função no container. Veja Criando com uma função.

Rotas e servidor

Toda rota dá 404 (menos a página inicial)

Causa: o servidor web não está mandando as requisições para o public/index.php.

Solução: com o servidor do PHP, use php -S localhost:8000 -t public (o -t public é obrigatório). No Apache, crie o public/.htaccess; no Nginx, configure o try_files. Veja Servidores web.

"Rota não encontrada" numa rota que existe

Causas: o método HTTP não é o mesmo (a rota é post e você chamou com GET, o que daria 405), o caminho tem um erro de digitação, ou o arquivo de rotas não foi carregado no bootstrap ($app->routes(...)).

Solução: leia a dica do erro: ela sugere rotas parecidas. E rode php vendor/bin/haki check para ver a lista de rotas registradas.

"Método não permitido" (405)

Causa: o caminho existe, mas com outro método. O cabeçalho Allow da resposta lista os métodos aceitos.

A resposta começa com HTML (ou um bloco escuro) antes do JSON

Causa: um haki(), echo, var_dump ou print_r esquecido no código. Também pode ser um espaço ou linha em branco antes do <?php em algum arquivo.

Solução: procure por haki(, echo e var_dump no projeto, e confira se todo arquivo começa exatamente com <?php.

Dados enviados

input() sempre devolve null

Causa: o cliente enviou JSON sem o cabeçalho Content-Type: application/json, então o corpo não foi lido como JSON.

Solução: envie o cabeçalho. No curl: -H "Content-Type: application/json"; no fetch: headers: { 'Content-Type': 'application/json' }. Para conferir o que chegou, use haki($request->all(), $request->headers()).

"JSON inválido no corpo da requisição" (400)

Causa: o corpo tem um erro de sintaxe (vírgula sobrando, aspas simples no lugar de duplas, chave sem aspas). A dica diz qual foi o erro.

Se a dica for "Malformed UTF-8 characters" e o texto tiver acentos, o problema é a codificação de quem enviou: alguns terminais do Windows (como o Git Bash) mandam o "é" fora do padrão UTF-8. Salve o JSON num arquivo UTF-8 e envie com curl --data-binary @dados.json, ou use Insomnia, Postman ou o próprio front-end, que enviam em UTF-8.

Recebo 422 e não entendo por quê

Causa: a validação recusou os dados. O campo campos da resposta diz exatamente o que está errado em cada campo.

Lembre que todo campo é obrigatório, a menos que tenha ->optional(), e que "" (texto vazio) conta como não enviado. Veja Obrigatório e opcional.

"O campo \"x\" não existe em ...Request"

Causa: você usou $request->x numa classe de validação, mas x não está em rules(). Só os campos declarados ficam disponíveis.

Solução: adicione o campo em rules() (com ->optional(), se ele puder faltar).

Login e tokens

"Token não informado" mesmo enviando o token

Causas:

  • Faltou a palavra Bearer e o espaço. O certo é Authorization: Bearer eyJ....
  • No Apache, o cabeçalho Authorization é descartado. Adicione ao public/.htaccess as linhas mostradas em Apache.

"Token inválido ou expirado"

A dica (em desenvolvimento) diz o motivo exato:

DicaO que fazer
"Token expirado."Normal depois de 15 minutos. Renove com o refresh token (veja o fluxo no cliente).
"Assinatura inválida"O token foi gerado com outro JWT_SECRET (por exemplo, o segredo foi trocado, ou o token é de outro ambiente). Faça login de novo.
"Token revogado (logout)."O usuário fez logout com esse token. Faça login de novo.
"Token malformado"O valor enviado não é um token completo: confira se não foi cortado ou se não enviou o refresh token no lugar do access token.

"O segredo JWT não foi definido" / "precisa ter pelo menos 32 caracteres"

Solução: rode php vendor/bin/haki key:generate. Ele grava um segredo forte no .env.

"Acesso negado" (403) para quem deveria ter acesso

Causa: o perfil no token é diferente do exigido pelo ->role(). A comparação é exata (Admin ≠ admin), e o perfil fica gravado no token no momento do login.

Solução: confira o valor em GET /eu e, se o perfil mudou, faça login de novo.

"A extensão pdo_sqlite não está ativa"

Causa: o login guarda os tokens num SQLite, e a extensão está desativada.

Solução: ative extension=pdo_sqlite no php.ini.

Navegador e front-end

"blocked by CORS policy" no console do navegador

Causa: o front-end está em outro endereço (por exemplo, localhost:5173) e a API não autorizou esse endereço.

Solução: crie o middleware de CORS e registre como o primeiro middleware global, com o endereço do seu front-end. Veja Exemplo: CORS. Se o erro só aparece em requisições com token, confira se o middleware responde ao OPTIONS e libera o cabeçalho Authorization.

Em produção só aparece "Erro interno do servidor"

Causa: em produção, os detalhes nunca vão para o cliente, de propósito.

Solução: leia o log do PHP no servidor (o caminho está na diretiva error_log do php.ini): o erro completo, com arquivo e linha, está lá.

Limitações e roadmap

Limitações conhecidas

  • O armazenamento SQLite padrão atende um servidor. Com vários servidores, use um TokenStore compartilhado.
  • Mudanças de perfil ou bloqueios só valem depois de logoutAll() ou da expiração do access token.
  • Só existe uma chave ativa por vez: trocar o segredo desconecta todos.
  • ORM e limitação de tentativas não estão incluídos.

Próximos passos

  • Query builder leve sobre PDO
  • Várias chaves ativas (rotação sem derrubar sessões) e ES256
  • Middleware de CORS e de limitação de tentativas prontos
  • Esqueleto de projeto: composer create-project shankscode/haki-app
  • Comandos make:controller e serve
